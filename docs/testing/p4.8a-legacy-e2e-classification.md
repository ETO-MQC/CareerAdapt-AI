# P4.8a E2E classification and canonical journey map

## Scope

This audit records which existing E2E files represent the current Hermes
production boundary and which are historical protocol fixtures. P4.8a does
not bulk-migrate or delete the historical suites. A file using the old
`/api/agent/stream` route or atomic tailoring tool names is not evidence that
the current production path is broken; it is a compatibility or history test
until explicitly migrated.

## Canonical current path

These are the current deterministic or hermetic references:

- `tests/e2e/agent-workspace.spec.ts` plus
  `tests/e2e/support/hermesRuntimeFixture.ts`: browser shell, profile intake,
  composer boundaries, and the production Hermes `run_start` /
  `run_events` / `run_status` contract. The tailoring fixture uses the
  high-level `career.workflow.tailor_resume` facade.
- `tests/e2e/p43d2-six-workflow-smoke.spec.ts`: typed quick-action dispatch
  and persisted workflow boundaries through `/api/agent/runtime/hermes`.
- `tests/e2e/hermes-p46h-integration.spec.ts`: Hermes semantic-agent routing
  for Profile Intake, general Resume composition, tailoring, Job Fit, and
  export; this is the canonical tool-path assertion suite.
- `tests/e2e/hermes-career-agent-eval.spec.ts`: hermetic capability/evaluation
  baseline. It is a runtime/evaluation gate, not a replacement for the
  user-facing journey below.
- `tests/e2e/p4-tailoring-engine-v2.spec.ts`: direct deterministic Resume UI
  journey. It now selects `steady`, `competitive`, and `max_fit` modes and
  answers bounded Max-Fit questions when shown.

The canonical tailoring semantic action is
`career.workflow.tailor_resume`; `create_tailoring_session` and
`answer_tailoring_question` are not current model-facing tools.

not deterministic and remains outside the hermetic gate.

## Canonical real-user acceptance journey

The acceptance path to exercise in one user session is:

1. Create or import a Profile; review source quotes and provisional facts;
   confirm the compact factual review; commit through the existing Profile
   write contract.
2. Generate a general Resume from the confirmed Profile and verify
   `experience → Profile → general Resume` factRefs/provenance lineage.
3. Select a target Job, run Job Fit, and inspect demonstrated versus
   confirmed-capability versus familiar/learning gaps.
4. Create a Job Resume from the general branch. Verify default
   `competitive` semantics, then run `max_fit` against a missing capability;
   answer one bounded question with a truthful option and keep the proposed
   wording at `resume_only` until explicit approval.
5. Manually edit a resume line and choose between current-resume-only and
   explicit Profile synchronization. Confirm no silent Profile overwrite.
6. Review meaningful diffs, preview, and export only after the final
   confirmation boundary; verify the source Profile and general branch remain
   unchanged unless the user explicitly requested synchronization.

The current repository has deterministic coverage for the domain and Hermes
facade boundaries. The single real-user quality acceptance in this section is
still a handoff requirement; no provider credential or user confirmation is
assumed by this document.

## Gate interpretation

- Current Hermes facade tests are canonical for routing and transport.
- Direct UI tests are canonical for deterministic Resume branch/revision
  behavior when they use current selectors and repository assertions.
- Legacy stream/atomic-tool tests are compatibility/history evidence only.
- Real-provider/Electron runs remain separate acceptance evidence and cannot be
  declared passed from deterministic fixtures.
