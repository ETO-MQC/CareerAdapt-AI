`SQLiteCareerPersistenceAdapter` lives in `poc/career-domain-persistence/`, implements the unchanged Port, and is never imported by a production composition root. The sole production-source change is optional Port injection into the existing WorkspaceRepository constructor; omitted injection still constructs DexieCareerPersistenceAdapter. There is no second Repository or copied business rule.

| SQL table | Structured columns | Payload / constraints |
| --- | --- | --- |
| profiles | id | primary key; validated CareerProfile |
| jobs | id | primary key; validated JobDescription |
| branches | id, profile_id, job_id, revision, current_revision_id | primary key; owner index; validated ResumeBranch |
| revisions | id, branch_id, revision_number, previous_revision_id | primary key; branch/number ordering index; validated ResumeRevision |

Schema version is `PRAGMA user_version=1`. Initialization runs in a transaction; unsupported versions fail without downgrading. Version 0 creates only these five tables; no workspace JSON blob or extra Dexie table. Non-initial migration is deliberately not implemented. Per current Schema, operation branchId is optional and its SQL column nullable. No extra branch/revision unique constraint or foreign key is imposed: current Dexie does not enforce these constraints, and Repository writes Branch before Revision. Reference/CAS/chain rules remain canonical business behavior. Primary-key writes use UPSERT matching Dexie put, not INSERT-only or delete-and-replace semantics.

Reuse the existing explicit tagged `canonical/decode` Codec from the prior isolated migration PoC without changing that file. Every container is tagged, avoiding user-content tag collisions. Preserve explicit undefined versus absent/null, Date versus ISO string, numbers versus strings, array order, nested objects, historical snapshots, and supported binary values. Unsupported values (e.g. functions, non-finite numbers, -0) fail explicitly; no JSON default coercion. Schema validation runs on write/read but the original value is encoded/returned, so validation defaults/unknown-key stripping do not silently rewrite storage. Domain times remain their exact Schema ISO strings. Canonical object-key ordering is the only representation change; parity ignores no fields.

## Transaction, CAS, receipt and error behavior

One SQLite connection serializes its units through a promise queue. Each unit acquires `BEGIN IMMEDIATE` before receipt lookup, read/CAS, business callback, Branch write, Revision write and Receipt write, committing only after callback success. Receipt replay and RevisionConflict remain the existing Repository implementation. Another independent connection/process waits asynchronously for the write lock (5ms acquisition checks, default 1000ms deadline); only BEGIN is retried, never the callback. A deadline surfaces SQLITE_BUSY; it is never reclassified as RevisionConflict. This avoids blocking the Node event loop while an async transaction on another local connection must finish. No arbitrary external IO belongs in a unit.

Every callback failure rolls back; rollback failure is an AggregateError preserving both errors. Public operation promises reject even though the queue's scheduling tail is settled to allow later operations. No error-swallow fallback or automatic business retry. Close/inspection refuses pending units.

Storage errors expose SQLitePersistenceError.kind plus original cause: SQLITE_BUSY (5), SQLITE_LOCKED (6), DATABASE_CORRUPT (11/26), OPERATION_ID_CONFLICT (unique operations.operation_id), SERIALIZATION (Codec/Schema boundary), or STORAGE. RevisionConflictError and other canonical business exceptions retain identity. Actual busy, duplicate key, bad-file corruption and serialization paths are tested; LOCKED and other numeric mappings are synthetic unit probes, not claimed real lock/corruption recovery certification.
