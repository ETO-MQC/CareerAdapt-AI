## 6. JD 长段落与标题：下一轮独立问题

用户补充现象：长 JD 按段归为一条要求，标题也成要求。已定位实际实现限制，**本轮只诊断记录，没有改分句、Prompt、Schema 或页面流程**：

1. `src/domain/jobOptimization/v4/analyze.ts:createLexicalJdUnits` 使用 `rawText.split(/\r?\n/)`，每个非空行只生成一个 Source Unit。单行 `熟悉Java。能够编写SQL；具备接口测试经验。` 在独立测试中仍是一个 Unit。
2. `reconcileJdSemanticLedger` 以既有 sourceUnitId 接受分类/父子关系。未知 ID 被拒绝，同一个 Source Unit 多个 assignment 报 duplicate_assignment；AI 没有在一段内部创建多个有独立 span 的原子要求的表达通道。
3. `src/app/jobs/JobsWorkspace.tsx:analyzeWithAi` **确实调用** jd-analyzer，传入 sourceUnits、groups、hierarchy，故不能直接说“完全没有给 AI 解析”。但是成功后主动把模型 `requirements` 清空，只消费 unitAssignments，再从图投影覆盖 requirements。这使模型即使能整理长段落，也不能通过返回 requirements 改变最终节点粒度。
4. `headingSection` 使用固定、锚定的标题词表和简短规则，未识别的标题可能落入普通 requirement；用户实际标题未提供，不能声称已复现那一个标题或判断用户当时 Provider 是否调用/失败。
5. AI 失败时仍保存本地图投影，UI 提示“岗位职责、条件和申请材料已经整理完成”，需要下一轮检查是否把本地结构化完成误呈现为充分语义分析完成。

下一轮建议：独立 JD 原子要求与标题闭环；以真实失败 JD 的脱敏样例建立“多句同段、标题变体、编号/分组/AND/OR、来源 span、AI 成功与失败”测试。先确定源码偏移可追溯的原子单元与 AI assignment 合并契约，再修页面展示/完成状态；保留原文、人工核对和 Repository 门禁。不能只改界面拆行，也不以新增 Prompt 禁令代替实现修复。本轮不自动开始。
