## 2. 根因及源码证据

- `JobDescriptionSchema`、`JobAnalysisDraftSchema`、`JobListingSchema`、JobCommitInput 强制非空公司，Facade 的 `!company` 提前返回，Reducer/WorkflowRegistry 也将公司列为必需。因此完整 JD 缺公司时不会进入正式提交。
- Facade 将解析完成、等待身份、等待确认和正式提交复用 transport completed 回执；原来没有独立 Repository 详情/列表回读作为业务凭证。
- Host 原来只保留 facadeCheckpoint，没有把 input.rawText、graph、identity 恢复到规范槽位，normalize 会回到 collect_job_description。
- `sameTurnTarget` 只诊断 tailor_resume 的同轮 JD 恢复，job_intake 的 absent 不是丢目标的直接证明。实际缺口是后续公司回复没有绑定原 Job 的补全入口，重发公司+JD 会改变 manual identity。
- 现有 executor 的写确认是真门禁；MCP 已有 pending write 的原请求保留/确认恢复能力，本轮复用。缺口为明确业务保存授权没有转换到该 Job 写入，而不是 transport、JSON-RPC 或 Runtime 不健康。
- `useWorkspace` 仅首次读取/显式 refetch，已挂载列表无订阅；活动直接渲染 Host 内容会露出工具名，默认确认标题也包含内部 Career 工具字样。
- 真实 JD 还暴露同一行编号项未拆分、C++ 未提取、至少一种语言被误判 all_of，以及第一覆盖段被冒用为身份字段来源。

这些是源码/回归证据；不能反向推断用户旧会话中必然存在或不存在某条数据库记录，本轮没有接管用户旧 IndexedDB。

## 3. 原故障与修复后的执行链

原故障：JD → parse completed → company 缺失提前返回 → 未提交 / 任务槽位丢失 → Agent 可能虚报 → 列表无正式 Job；补公司无可靠原实体入口 → 确认未完成仍可能被误读为成功。

当前：Hermes → MCP → CareerToolGateway → 原 Job Intake Facade → 原 Parser → 原候选摄取/分析草稿/转换确认 → WorkspaceRepository 事务 → 正式 Job → 独立 get/list 核对 → committed checkpoint → Host 持久化 → 列表订阅。后续公司回复使用当前持久 TaskState.selectedEntities.jobId；不依赖相邻消息猜测，也覆盖模型重传旧 JD 的情况。

## 4. Job 契约与字段处理

| 字段 | 本轮语义 |
|---|---|
| 原始 JD | 核心输入，原样保留；解析/提交失败仍保留在任务或用户消息；空/无可提交要求不会成为正式 Job |
| 岗位名称 | 可从原文提取；无可靠名称使用“岗位名称待补充”，identityEvidence 标记 missing；正文推导名称标记 derived，不能冒充明确标题 |
| 公司 | null 或未提供；Public Facade/Parse/Commit、Domain、Draft、Listing、公共摘要和 UI 贯通；UI 显示“公司待补充”，不持久化假公司 |
| 毕业年份、专业、学历、技能 | 原要求与 sourceSpan 保留；区分硬约束、普通要求和优先；不扩充原文未给事实 |
| 招聘批次、地点、薪资、投递时间 | 可选；已有图谱/元数据与原文承载，缺失不阻断；不新建平行字段库 |
| 身份来源/确认 | identityEvidence 保留 jd/user/derived/missing、引用、必要用户消息 ID 与 confirmed。公司补全记录用户来源，原JD不改写 |

健康状态只派生：身份或语义待核对为 WORKABLE；完整且无需审核才 READY；原文/可用解析缺失为失败/输入阻断，不把公司缺失当 BLOCKED。没有新增 Dexie 表、迁移、生产依赖或另一套 Job 数据库。Resume Schema v2、Fact Guard、Profile 事实与 PDF 逻辑未改。

## 7. TaskState、Confirmation 与成功语义

transport/tool receipt 保留原协议；新增业务 checkpoint 的 businessStatus、persistenceVerified 是独立语义。只有详情与列表均读到正确 jobId、原文、标题、公司、graphHash/版本后才 committed。缺少权威观察的 completed 被判未核验，不能进入保存完成叙述。

Host 恢复 rawText/graph/身份与 jobId/revision，后续公司回复继续原任务；没有正式提交凭证时，保存成功叙述替换为“岗位信息已经整理，但尚未完成保存。当前资料已保留，可以继续完成保存。”

明确“先保存岗位”以及岗位录入动作属于用户授权；仅授权新建或目标明确的空公司补全。覆盖既有公司、歧义和冲突仍需确认。原 MCP pending write/continuation/CAS 不绕过、不重写。确认描述保存/更新当前岗位，内部错误保留诊断，用户文案可理解。

活动仍归属于原 Assistant Turn，保留原紧凑折叠组；Host 不再生成“正在调用 toolId”，界面只显示处理/整理/核对/失败/有凭证的保存完成。Assistant 内部工具载荷和错误码不直接呈现，用户原始消息保持原样。岗位确认标题为业务行为。
