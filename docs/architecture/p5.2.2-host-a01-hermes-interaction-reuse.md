## Shell与Chat组合结论

原生Sidebar同时承担产品菜单与必要的profile/project/session功能。两者可以在JSX组合层拆分，但不能直接移除其状态、搜索与native actions。本轮替换其应用导航组，原session段只在Chat视图显示；保持Memo surfaces和latest-actions稳定引用。Home/Profile属于完整页面，新增Home必须保留路由分类；原Chat路径保持不动，避免复制会话路由或重建会话选择逻辑。

Settings/Agents/Command Center等是`useOverlayRouting`管理的native overlay，继续使用其原路由与返回语义。新Career导航调用原`onNavigate`，不维护第二个router。Root Providers均保留；此切片不要求Main/Preload修改。外部源码41项、Main/Preload和默认开发Renderer入口均有机器哈希，不能将Gateway ready标记等同于完整Runtime发行资格。

## 附件链

原生`chat/composer/context-menu.tsx:ContextMenu`保留 Files、Folder、Images、Paste image、URL、Prompt snippets 和插件attachment providers。文件选择回调由ContribWiring交给`useComposerActions`的`pickContextPaths`；ChatView的`useFileDropZone`区分workspace相对引用和OS绝对文件，OS文件进入附件处理而非把路径原样当资料提交。

`useComposerActions`与`store/composer.ts`持有每线程附件，图片支持预览、取消/移除与错误通知；`uploadComposerAttachment`及`syncAttachmentsForSubmit`处理本地/远端文件引用、`file.attach`/图片字节路径、uploadState、attachedSessionId、提交前等待已有上传，避免重复发送。`composer/attachments.tsx`负责附件显示。重试、多个附件和消息绑定均属于该原生链，Shell不另写上传器。

本轮实际只打开原生附件菜单并截图，没有选择文件、拖放、上传、解析或使用真实附件历史。以上后半链为源码结论及已有确定性测试覆盖，不是本轮端到端文件处理PASS。

未来职业资料接入必须是：native attachment→受控staging/attachmentId、内容hash及来源→MaterialIntakeService.prepare/OCR/AI→Schema校验与来源定位→Fact Guard/人工核对→明确用户提交→WorkspaceRepository。需要绑定person/profile/session/task，取消和迟到结果隔离，拒绝路径/字节直入职业工具。附件进入原生对话不等于已入职业资料库，也不意味着有权将内容发送到OCR/AI服务。
