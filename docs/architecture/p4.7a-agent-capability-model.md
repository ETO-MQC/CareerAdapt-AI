# P4.7a Agent Capability Model

Status: implementation decision for the CareerAdapt AI P4.7a closure.

## Decision

CareerAdapt keeps one semantic Agent: the Hermes Agent loop hosted by the
CareerAdapt Host. The fixed ownership chain is:

`CareerAdapt Host → Hermes → Hermes Skills / Toolsets → CareerAdapt MCP (and future MCP servers) → Domain / Workflow → WorkspaceRepository / Guards`

There is no CareerAdapt semantic router, intent classifier, planner,
coordinator, second runtime, or CareerAdapt Plugin SDK. A normal user message
enters one Hermes turn. Hermes may answer directly or request visible typed
tools. Deterministic UI actions such as confirm, cancel, accept, reject, and
branch selection remain host actions and bypass semantic reinterpretation.

## Upstream reference review

The current upstream implementations and specification were reviewed for the
shared pattern rather than copied as frameworks:

- Hermes Agent: the [agent loop](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/run_agent.py)
  delegates tool definitions and calls to the [tool registry/model-tools
  layer](https://github.com/NousResearch/hermes-agent/blob/main/model_tools.py);
  [toolsets](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/toolsets.py)
  and [MCP integration](https://github.com/NousResearch/hermes-agent/blob/main/tools/mcp_tool.py)
  provide the extension surface. Hermes [Skills](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/creating-skills.md)
  are on-demand `SKILL.md` procedures whose metadata helps determine when to
  load them. Native MCP configuration supports include/exclude filtering and
  coexisting servers, as shown in the [MCP guide](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/guides/use-mcp-with-hermes.md).
- OpenClaw separates model-visible tool policy from Skills and Plugins:
  [tool profiles and allow/deny policy](https://github.com/openclaw/openclaw/blob/main/docs/gateway/config-tools.md)
  constrain the model surface, while [Tools, Skills, and Plugins](https://github.com/openclaw/openclaw/blob/main/docs/tools/index.md)
  assign typed operations, procedures, and code/credential/lifecycle
  integrations respectively.
- Codex provides a useful conversation vocabulary: a [Thread contains Turns,
  and Turns contain Items](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md).
  Its app-server contract also demonstrates [dynamicTools, deferLoading, and
  Skill inputs](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)
  without requiring a second semantic loop.
- MCP remains model-controlled at the protocol boundary: [tools/list,
  tools/call, and tools/list_changed](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
  provide discovery, invocation, and refresh semantics.

The adopted pattern is therefore: one Agent loop + typed tools + on-demand
Skills + MCP extensions.

instructions.

## Skill routing contract

Skill frontmatter descriptions are the first routing signal and are now
intent-oriented and mutually distinguishable:

| Skill | Use for | Do not use for |
| --- | --- | --- |
| `candidate-profile-interview` | Create/complete CareerProfile or answer an active Profile Intake question | Story-only extraction, Job Fit, Resume work |
| `career-story-mining` | Extract actions, methods, challenges, results, and evidence from one described experience | Profile writes, Job Fit, Resume work |
| `job-fit-analysis` | Compare confirmed evidence with a Job/JD without changing a Resume | Resume creation/tailoring or general advice |
| `resume-tailoring` | Create/tailor a job-specific Resume for a supplied/selected target | General Resume, Job Fit-only, untargeted review |
| `resume-review` | Review/improve an existing general Resume without a target Job | Target Resume, Job Fit, import, new composition |
| `resume-composition` | Create/update a general/base Resume from confirmed Profile evidence | Target Job/JD Resume, Job Fit, import |

Skills describe user-level semantics and call only visible high-level Facades
(plus the smallest read surface when necessary). They do not instruct Hermes
to call CareerAdapt atomic implementation tools. Tailoring may begin directly
from a pasted JD; Job Fit is not a hidden prerequisite. Resume Review uses the
existing `career.workflow.compose_resume` contract with
`mode: "general"`, `sourceResumeId`, and
`generalResumeMode: "update_existing"`.

## Resume Review decision

No `career.workflow.review_resume` Facade was added. The existing
`compose_resume` input already accepts `sourceResumeId` and
`generalResumeMode: "update_existing"`; the existing confirmed-write tests
prove that this mode preserves the explicit user selection and creates the
isolated update revision. This gives Review one high-level capability without
exposing the underlying composition/review atomics or introducing another
workflow engine.

## Conversation and prompt boundary

There is one conversation model and no pre-read router. Hermes receives the
user turn first; it asks for a Career read only when the answer needs confirmed
personal context. Greetings and general advice therefore remain tool-free.
`careerRunInstructions()` remains the short invariant prompt for natural
conversation, evidence safety, receipt-backed writes, host ownership, and
Hermes tool selection. Intent-specific guidance belongs to Skill metadata,
Skill content, and Facade descriptions.

Measured `careerRunInstructions()` size is unchanged at 21 physical lines and
1,772 characters before and after this phase.

The deterministic hermetic matrix covers:

| Case | User intent | Expected Career path |
| --- | --- | --- |
| A | `你好` | Direct answer, zero tools and zero reads |
| B | General career advice | Direct answer, zero Career tools |
| C | Personal career question | Read-only Profile/context tool |
| D | Build a Resume from zero | `profile_intake_turn` high-level Facade |
| E | Review an existing general Resume | `compose_resume` with `update_existing` |
| F | Paste a JD and create a target Resume | `tailor_resume` high-level Facade |
| G | Compare fit with a Job | `job_fit` high-level Facade |
| H | Export a Resume | `resume_export` high-level Facade |

## Future MCP proof

Hermes' native MCP server configuration is the extension point. A second
MCP server (the test fixture uses `calendar-test`) can remain beside the
managed `careeradapt` server. The companion config writer preserves the
user-owned server block and refreshes only CareerAdapt's managed entry. No
change to `HermesCareerAgentRuntime`, `AgentRuntimeRouter`, AgentHostStore
semantic routing, or `careerRunInstructions()` is needed. Future Skill/tool
metadata may describe the added capability; the Agent loop stays the same.

## Verification contract

The P4.7a contract test parses all six production `SKILL.md` files and checks
that every explicit `mcp__careeradapt__*` reference is in the current
production catalog and is either a high-level Facade or an approved read. The
same suite checks the production profile, Skill descriptions, review decision,
routing collision fixtures, and second-MCP coexistence. Hermetic Hermes E2E
cases, runtime smoke/integration, P4.6b tailoring golden, typecheck, lint,
build, unit tests, and diff checks remain required acceptance gates.
