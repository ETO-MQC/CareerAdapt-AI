## 3. 修改前后数据流

之前：JobsWorkspace 按经历容器筛 Profile→旧 matcher 按最佳候选词数给等级→可选旧 AI 再评估→正式 RequirementMatch；资料库推荐/Agent Fit 另走 V2/Core-02，页面读取持久结果仅按 branchId，组合条件与 stale/异步选择可能丢失。

现在：当前 Profile + 当前可见 Branch snapshot（或稳定、只在内存存在的资料库投影）+ JD-01 canonical Graph→既有 CandidateEvidenceUnits→召回（含只用于召回的标签/同义/相关信号）→逐条件、正式事实成熟度与充分性评估→既有 V2 matrix→Core-02 CandidateEvidenceMatrix/JobFit。页面、资料库推荐和 Agent Fit 使用这一分析；正式匹配仅投影进原 RequirementMatch，由原 Repository 在显式生成操作中保存。

只读查看不调用模型、不保存匹配、不创建 Branch、不修改 Profile。旧正式记录可继续读取；页面重新计算 stale，展示当前版本的只读结果。迟到保存可以保留原操作的记录，但选择已变则不再启动后续生成或改当前显示/路由。

分析身份使用 profile revision、job version、Graph hash、branch id/revision/currentRevisionId 与 Core-02 ruleVersion；页面请求令牌另外包含 MATCHER_VERSION。岗位版本增加内容指纹，避免仅 updatedAt 相同掩盖 Graph 改变。旧 RequirementMatch 字段未删除，v1.1 等旧结果自然 stale，不做数据迁移。

显式布尔技术条件由各必要项的正式 demonstrated 事实及当前可见证据共同判定；检索分用于召回，不再把“命中两个词”当充分性。保留原召回门槛、非布尔 direct 门槛及安全阈值，没有为通过失败测试降低阈值。
