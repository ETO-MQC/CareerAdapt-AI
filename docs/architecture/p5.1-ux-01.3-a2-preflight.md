## 2. A2-F 的实际缺口

这不是 Resume Schema v2 无法保存 title/date，而是**现有事实确认契约尚未绑定通用简历的字段更正**：

1. `preciseResumeEdit.ts` 的选择仅允许 project/work/internship 的 description 与单 highlights；提案固定 precise-edit-v1 和 presentation_only。不能扩大旧版本解释来放行事实字段。
2. `tailoringDiff.ts` 的 isAllowedPath 明确排除身份和事实字段；title/date 不能套用 replace rewrite。`tailoringStructuralPreservation.ts` 还明确保护这些字段。
3. `tailoringClaimPolicy.ts` 将新数字、岗位、组织和责任升级列为 hard fact，用户点击措辞确认不能消除 hard-fact 阻断。
4. `factProposal.ts` 有可复用的 clarification、来源、过期和明确确认机制，但 scope 仅为 job_specific / profile_sync_candidate。不存在指向 general Branch 的 resume_only 字段更正契约。不能把 general 伪装成 job_specific，也不能未经决定将 profile_sync_candidate 改解释为通用简历更正。
5. `WorkspaceRepository.createPendingConfirmation / consumePendingConfirmation` 可复用现有 appMeta 信封与 consumed 恢复，但 A1 精确提交事务目前不读取它们，且缺少 Fact Proposal 与 branch/base/field/value/proposalHash 的原子绑定。

附件 §3.2 明确要求：“如果现有 Claim Safety 无法支持某种事实更正，先定位实际缺口，不得绕过原有保护机制，也不得自行建立未经批准的确认协议。”因此本轮未自行实现新的事实确认作用域。**只暂停该事实契约决策，不宣称技能或 bullet 技术上不可实施。**

## 3. 建议的最小兼容方案（待用户决策，未实现）

建议批准“仅目标简历的事实更正”契约扩展，复用现有 Fact Proposal 确认机制：

- 新事实更正使用明确版本的领域提案，旧 precise-edit-v1 的 Schema、Hash、解释与恢复保持原样。
- Fact Proposal 的新版本增加 resume_only 作用域；不改变旧 fact-proposal-v1 两个 scope 的解释。不增加数据库表、迁移或 Resume/Profile 正文 Schema。
- 新作用域必须绑定 session/task/turn、profile/version、branch/purpose/job、baseRevision/branchRevision、section/item/field、原值、新值、operationId 与完整提案 hash；模型不能提供这些身份或确认结果。
- 证据来自 Host 读取的已确认事实、来源记录，或可信捕获的用户原始纠正声明。模型生成的解释不作为证据；缺证据保持待核对。
- 区分同精度格式规范化、已有确认来源支持的字段更正、用户声明的新纠正；不得统一标 presentation_only。
- 继续使用原有明确确认动作及确认信封，不新建工作流引擎。明确确认同时绑定原始纠正声明/证据与精确修改；改值或改来源必须重新审核。
- 在 A1 专用提交事务中校验并消费对应确认记录、重新读来源与版本、校验字段/日期，再复用 createResumeRevision。确认消费与正式写入任一失败整体回滚；已提交恢复只回读原操作回执。
- 新确认结果仅用于所选 Branch，不创建或更新 Profile 事实，不授权 Profile 同步，不将新事实伪装为 Profile 已确认事实。
- 日期只允许确切表达的年/月/日精度；不得补齐未知日期。需校验真实日历日期、起止关系、current 语义、规范化前后含义和精度一致；不以导入解析器的月级投影代替日精度验证。

替代方案：本轮 A2-F 仅支持可从现有已确认 Profile 及来源精确核验的更正/同义日期规范化；新纠正事实继续走既有资料核对流程。该流程若要求更新 Profile，必须由用户独立触发。此替代方案不能关闭附件全部事实更正验收，A04 必须继续标为未完成。
