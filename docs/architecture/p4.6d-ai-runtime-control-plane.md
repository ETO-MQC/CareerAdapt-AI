# P4.6d AI Runtime Control Plane Simplification

## Scope

P4.6d removes renderer-side runtime orchestration from Settings and keeps the
existing Web/Electron transport, local settings record, Supervisor, MCP/domain
boundary, and RuntimeStatusStore. It does not add a provider abstraction,
secret migration, dependency, Dexie table, or second runtime.

## Authority and flow

```text
Settings draft
  -> normalize/validate
  -> one update_config command
  -> HermesSupervisor (single-flight, stage, replace, read back, commit/rollback)
  -> Supervisor status observation
  -> AgentRuntimeProvider
  -> RuntimeStatusStore
  -> Settings / topbar / AI Agent diagnostics
```

`HermesSupervisor.runtimeConfigState.active` is the only active runtime
configuration authority. A health response can observe readiness and provider
diagnostics, but cannot overwrite Supervisor-owned active configuration or
readiness. `RuntimeStatusStore` is the single renderer projection. Settings
does not reconnect MCP, poll health, fetch runtime config, or hydrate a draft
when the settings category changes.

`CandidateProviderTestResult` is separate from active state. `/api/ai/test`
probes the submitted draft and returns a local result; it does not stage,
restart, or publish active runtime state.

## Apply semantics

Save & Apply validates and writes the existing local draft, interrupts one
active semantic Run only after explicit confirmation, and sends one
`update_config` command. The Supervisor owns the transaction and returns a
safe receipt. During replacement, the old Active configuration remains
visible while the new Desired configuration is applied. A verified readback
swaps Active; provider/readiness failure gets one bounded rollback to the
previous healthy configuration. An already active, Ready configuration is a
no-op. There are no post-save reconnect or refresh commands.

The user-facing path is compact: AI model, current model, URL, API key, model,
candidate test, Save & Apply, and a More section for protocol/default/env/key
maintenance. AI Agent shows Ready/Running/Career-tool summary, one primary
lifecycle action, and collapsed diagnostics/More sections. Fingerprints,
generations, source, dimensions, counts, and raw reason codes remain
diagnostic-only.

## Reference basis

The refactor takes only the useful boundaries from these existing systems:

- [OpenAI Codex config state](https://raw.githubusercontent.com/openai/codex/main/codex-rs/config/src/state.rs): effective configuration and origin-aware state.
- [OpenAI Codex app-server config protocol](https://raw.githubusercontent.com/openai/codex/main/codex-rs/app-server/README.md): read/write commands with explicit, versioned results.
- [Continue ConfigHandler](https://raw.githubusercontent.com/continuedev/continue/main/core/config/ConfigHandler.ts): one cascade/config controller with published updates.
- [Jan provider documentation](https://raw.githubusercontent.com/janhq/jan/main/docs/src/pages/docs/agent/providers.mdx): provider endpoint/key/model configuration boundary.
- [Open WebUI provider setup](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/): endpoint, credential, and model as the minimal provider UX.
- [LibreChat configuration](https://www.librechat.ai/docs/configuration): explicit restart/apply semantics for runtime configuration.

CareerAdapt retains its own Supervisor, Resume Schema v2, evidence boundaries,
and Web/Electron contracts; no external runtime protocol is introduced.

## Verification target

Focused regressions cover the pre-change Settings flicker, twenty navigation
switches, twenty Save clicks, candidate isolation, route-away during apply,
active-Run interruption, old-Active visibility during replacement, single
flight, same-config no-op, readback-gated apply, and bounded rollback. Full
validation and real-provider/Electron acceptance status are recorded in
`history3.md`.
