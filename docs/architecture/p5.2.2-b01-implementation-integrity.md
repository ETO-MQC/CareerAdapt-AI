# B01.1 — Implementation / Business Data Integrity

2026-11-07。范围：现有 confirmed apply 的请求绑定、回执重试和来源回放。整体B01仍PARTIAL。

## 新实现

1. `ResumeBranchOperationSchema.tailoringRequestHash` 为可选元数据；不新建表、不迁移旧记录、不更改Resume正文Schema v2。
2. `applyTailoringDiffs` / `deriveAndApplyTailoringDiffsAtomic` 在事务外对稳定序列化的完整请求计算既有hashText指纹，在原事务内保存。重复operationId先核对指纹，相同请求重放，不同来源/岗位/版本/Diff/确认集合拒绝为 `tailoring_operation_conflict`，不创建新Branch/Revision/operation。
3. derive回放从既有previousRevision snapshot重建原内容hash，不再读当前通用简历内容。
4. `BrowserAgentToolService.applyTailoringChanges` 每次仍执行Repository绑定、CAS路径与结果回读。已存在的artifact receipt只复用其完成时间，再交给原不可变receipt保存校验；没有用旧receipt跳过验证。

没有改变Fact Guard/Claim Safety、来源确认、review ledger、selectedDiffs不受信原则、General/Profile隔离、TaskState或现有用户确认入口。模型与Renderer没有新增Grant或生产权限。hashText用于幂等比较，不是身份凭证或Native可信用户授权。

## 已验证

- derive相同请求重试返回原Revision与相同before/after hash。
- 同ID换job/source/sourceRevision/diff被拒绝，Branch/Revision/operation计数不变。
- 已有岗位分支更新后的同请求重试重放；不同diff/branch被拒绝。
- 历史无请求指纹的operation仍可读取；在这两条apply路径上拒绝不具备输入绑定证据的重放，不推断其为未执行，也不自动重执行。
- 首次真实Service apply后，用新Service/Repository实例重试，artifact receipt完全相同、Revision ID相同。
- 写入已完成但回读故障时不生成成功receipt；恢复读取后同ID重试可完成原产物，分支数不增加。
- 原结构化项目、日期、工具、A4 HTML语义、source branch隔离断言保留。

## 兼容限制与未完成项

旧operation没有可靠完整payload时返回冲突是有意的安全收窄：应读取既有产物/receipt核对，不能换新operationId重新应用未知操作。未修改其他Repository方法的通用幂等协议。

当前回放仍返回Repository当前Branch搭配原Revision；若结果分支已被后续编辑，Service现有readback会拒绝不一致而不是报告成功。本轮未扩张为全仓历史结果重建。请求指纹不是全局exactly-once保证。

单位测试的合成fixture可直接初始化Revision；正式被测写入仍使用真实WorkspaceRepository/Dexie事务，没有Mock掉Repository。Browser Route A/B使用隔离测试上下文与产品UI，未访问真实用户Profile。真实用户确认→apply→PDF的浏览器闭环仍未验收；Native Host资格不变。

最初Repository红测错误是“本应拒绝却返回成功”；首次修复曾把Revision.snapshot误当完整Branch造成Schema失败，已修正并保留说明。第二项红测准确抛出 `resume_artifact_receipt_immutable_conflict`；修复后通过。没有删除断言、增加skip或降低阈值。

并发相同apply由两个Service同时执行，返回同一不可变receipt/Revision且仅一个岗位分支；checkpoint更新时间独立使用本次观察时间，保证故障恢复状态可单调推进。实现中曾把稳定业务完成时间同时用于checkpoint更新时间，恢复断言发现状态未前进，已修正，未弱化断言。
