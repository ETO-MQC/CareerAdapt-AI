## 3. 八条关键链路与持久化落点

### 3.1 普通问答

`AgentComposer` → `AgentWorkspace.submit` → Provider `runTurnOnce` → Hermes Runs。普通文字原样进入Hermes；只有模型选择Career工具或用户显式启动工作流才产生对应任务。会话历史经 `activeBranchContext.ts:buildActiveBranchContext` 排除撤回/被替代消息；`careerSessionBinding.ts` 优先使用持久化会话人物/Profile身份，页面只检测不匹配，不隐式换人物。会话与活动Run由 `AgentSessionStore`/Repository持久化；普通问答不必写Profile或Resume。模拟A/B两项通过且断言工具数0。

### 3.2 从简历导入入口上传

`src/components/resume/import/ResumeImportWizard.tsx:prepareWithOrchestrator` → `ResumeImportOrchestrator.prepare` → 按格式提取 PDF/DOCX/JSON/文本，按选择使用文本、视觉识别或本地OCR/本地路线 → semantic mapper/规范字段映射、来源定位与覆盖诊断 → 保存 `ImportedResumeDraft` → 人工核对基本信息/条目/字段/未分类项 → existing人物进行reconciliation或选择new人物 → `confirmImport` → `WorkspaceRepository.confirmImportedResume`。

Repository基于draft revision、reconciliation revision、目标人物和operationId确认，提交来源/事实/Profile并按用户选择创建通用ResumeBranch及首个ResumeRevision；结果返回profileId/branchId供编辑器打开。导入是用户显式选择目标的动作，不是简历编辑隐式同步Profile。当前入口并非“上传就直接覆盖简历”。

### 3.3 在AI对话中上传

需区分当前实际UI与旧/显式入口：

1. 当前Hermes Ready状态下，`AgentWorkspace.tsx:292–335` 将File注册到 `AgentAttachmentStore`，询问AI隐私偏好后调用 `host.runTurn`，传附件ID/名称/MIME/大小及purpose，不传文件字节。
2. Provider `runTurnOnce`仍走Hermes；API route仅将安全引用放入 `career_context.attachments`，提示只有明确要求导入才用附件ID。**附件不会自动变成Hermes本地路径或模型原生文件输入**。
3. Hermes若调用 `career.workflow.resume_import` → Facade调用 `career.resume.import.prepare` → `BrowserAgentToolService.prepareResumeImport` 解析附件ID、偏好、canonical JSON → **同一个 `ResumeImportOrchestrator.prepare`**。成功后释放内存File，返回importId/draftRevision/review artifact。
4. 核对/确认沿现有导入UI及 `commitResumeImport` → 同一个 `WorkspaceRepository.confirmImportedResume`。因此解析与正式提交已共享，不需要从零重建另一条parser。
5. `AgentHostStore.dispatch(composer_submit)` / `resolveDirectImportAttachment` 仍有显式导入的确定性通道：直接执行resume_import facade，不经过语义Run。`p47c1-import-execution-boundary.test.ts`证明这条通道能本地读取真实DOCX并进入核对，**不能用该测试证明当前Hermes聊天附件自动按意图完成相同闭环**。

附件生命周期：`AgentAttachmentStore.ts`两张内存Map；ID与agentSessionId绑定，丢失抛 `agent_attachment_lost`，跨会话抛 `agent_attachment_session_mismatch`。同一页面存活期间会话切换与浏览器刷新是两回事；刷新/重载后尚未转成持久draft的File不可恢复，需重新选择。成功prepare后的草稿可恢复不等于原附件持久化。当前目的标记常为career_evidence，模型是否正确把“上传并优化”衔接导入/编辑、以及仅上传时是否只问一个问题，真实端到端未证实。

### 3.4 AI修改简历

存在不同契约，不能笼统称“AI输出一个简历JSON”：

- 正文规范：`resumeV2.ts` 的 `ResumeBasicsV2Schema`、`ResumeItemV2Schema` 和canonical field目录。
- 导入/导出交换：`resumeJsonV2.ts:CareerAdaptResumeJsonV2Schema`，版本 `careeradapt-resume-v2`，strict、section/item类型一致和ID唯一；不是模板专用正文Schema。
- 岗位字段差异：`schemas/tailoring.ts:ResumeTailoringDiffSchema` strict，target为sectionId/itemId/受限fieldPath，携带original/value/requirementIds/evidenceRefs/supportLevel；模型单次diff输出最多1项（`ResumeTailoringDiffModelOutputSchema`）。
- 通用组装：`CareerResumeWritingService`调用结构化AI，输出 `CareerResumeWritingOutputSchema` 的summary/assets，然后Writer/Reviewer映射到V2 item与claim ledger；它是完整组装工作流，**并非所有AI编辑均为字段级patch**。

定向修改入口：Facade `executeTailoringResumeFacade` / `tailoringWorkflowDriver.ts` → BrowserAgentToolService的session/diff生成/预览/应用 → `WorkspaceRepository.applyTailoringDiffs`或派生分支路径。`repositories.ts:2969`要求branchId/jobId、expectedBranchRevision、expectedRevisionId；事务内检查job_specific归属、revision+revisionId，逐项校验original/path/type/evidence/confirmation，通过后patch既有内容并创建链式ResumeRevision。派生路径保留sourceBranch/sourceRevision和presentation不变量；原通用分支不反写。失败无有效patch时不创建版本；operationId用于幂等。

**源码发现的不同边界：**

- 通用 `composeResume(mode=general,generalResumeMode=update_existing)` 在 `agentToolService.ts:941附近` 调用 `ensureGeneralResumeFromProfile`，没有传sourceResumeId或提案基准ResumeRevision。
- `repositories.ts:3487–3528` 的ensure方法签名也没有这些字段；update_existing自行选择该Profile下active general中updatedAt最新的一份，并用执行时读到的revision调用mutate。Repository CAS仍有作用，但不是对用户审阅提案时的目标/基准做CAS。
- 更新会重组Profile-derived内容并保留部分manual/有编辑痕迹条目；不是只修改用户指定字段。因此“选A，B后来更新，最终更新B”的目标风险，以及“提案后A编辑、确认时仍用旧提案”的版本风险需要优先复现。**缺失目标/提案版本参数为源码证实，真实误写/字段丢失事故尚未复现**。
- 现有 `resumeCompositionConfirmedWriteP45c12.test.ts` 有单一general分支update_existing和stale checkpoint测试；单份分支的通过不足以覆盖多分支选定目标与ResumeRevision并发。

### 3.5 粘贴JD

两种入口：岗位UI与Agent。Agent原子 `parseJobDescription` → `analyzeJobCommand`（`services/jobs/tailoringCommands.ts`）→ V4 lexical/semantic ledger（`domain/jobOptimization/v4/analyze.ts`）→ `JobRequirementGraphV4Schema`。图含sourceSpan、语义单元、职责/必备/优先及关系、覆盖与needsReview/graphHash，不将缺项自动当候选人事实。

## 4. 资料检索、事实来源与表现一致性

### 4.1 资料库与Fact Guard

`career.context.retrieve` → `BrowserAgentToolService.retrieveCareerContext` → `domain/careerContext/retrieveCareerContext.ts`。这是确定性、词项相关度检索，maxFacts默认12、上限24；返回factId/sourceEntityId/evidenceRefs、Profile版本、Job与Resume摘要、unknown/unsupported提示；不写Profile，不是向量检索。`careerContextBindingResolver`优先会话pinned/requested/active/single，歧义返回choice，不靠文件名猜人。

`ResumeEvidenceGraph.ts:buildResumeEvidenceGraph`从Profile structuredFacts与factIds/provenance构图，排除未确认/高风险和不成熟占位内容；事实确认还检查provenance.confirmedByUser。Writer映射claim/source，Reviewer处理去重、贡献/数字/工具声明与证据不足；`domain/adaptation/factGuard.ts`规则检查新增数字、实体、工具/技能、归因/所有权等，生成blocked_high_risk/needs_edit/pass。规则和AI辅助审查不会替代人工确认。无阈值变更，无第二事实数据库或自动把简历反写Profile。

六个职业Skills沿现有Hermes按需加载；本轮未更写Skills，也未验证锁定版长期memory中的真实用户数据内容。不能承诺现有规则能识别所有语义虚构；真实质量/盲评缺证据。
