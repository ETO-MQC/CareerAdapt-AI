## 2. 实际支持范围

| 操作 | 支持范围 | 限制 |
|---|---|---|
| 事实更正 | project.title / role / organization / startDate / endDate；work 与 internship 的 role / organization / startDate / endDate，共 13 组合 | 当前正式 Branch/Revision，已有非空字段；用户直接提交确切新值，明确确认后仅用于所选简历 |

| 单条 Bullet 删除 | project / work / internship.highlights 的单一原 index | 原数组、索引及基准版本绑定；重复文字仍按原 index 区分 |
| Bullet 排序 | 上述三个 section 的完整原索引排列 | 每个索引恰好一次；从原数组派生，不接受模型传回正文数组 |

13 个事实字段组合全部做 Schema→目录→Validator→Repository 往返。六个 section/结构操作组合有实际 Repository 验证；四类操作均覆盖 general 和 job-specific，包含通用与两个岗位分支隔离。

不支持空字段补写、其他 section/字段、学历/证书/数字成果/能力等级/职责描述升级或历史 Revision 原地编辑。名称字段限制长度及明显的复杂成果/责任表达。日期校验真实日历、年/月/日精度与起止关系；不补缺失日期，不将“至今”推断为日期，不通过改结束日期改变 current 状态。进行中的经历可保留 current；current=true 时拒绝填入结束日期。

日期同精度格式规范化与真实日期变化分别标记 `date_normalization` / `user_declared_correction`。不将事实更正标为 presentation_only。

技能复用 canonicalTechnicalTerm 去重。SQL 与大小写/空白变体、Node 与 Node.js 复用既有规则；SQL 不等于 MySQL。无法唯一关联或来源失效时拒绝。maturity 为 learning/familiar 不自动作为已掌握技能加入；这与技能 level 的 basic/familiar/proficient 不是同一字段，已有等级不升级。

## 3. 版本化契约与可信边界

旧 `precise-edit-v1` 的文件、Schema、Hash、解释及恢复规则保持不变，旧 `{ proposedValue }` Facade 输入继续有效。旧 `fact-proposal-v1` 的 Schema、scope 和意义不变；共享确认函数仅泛化 TypeScript 参数，过期/重复/空答案检查及原运行行为保持。

新增独立 `precise-edit-v2` 与 `fact-proposal-v2 / resume_only`，由兼容分派层路由；不将旧提案转换成新语义。v2 每个提案绑定 session/task/turn、Profile/version、Branch/purpose/job、baseRevision/branchRevision、section/item/field、原值或完整原数组身份、操作、证据、operationId 与完整 SHA-256。

模型输入仅允许所选类型的值/排列，不能提供 Branch、item、sourceSkillId、evidenceRefs、operationId、事实分类或确认结果。技能新增和删除甚至不接受新正文。Host 的明确目标与 Repository 权威回读决定身份；未知类型、额外字段、跨类型载荷、错 Hash、错引用、来源不符及 stale 均失败关闭。

继续使用 TaskState 的唯一完整待执行提案、原三处引用和确认状态。正式提交后追加的审计是历史只读记录，不是新的执行权威或恢复写入引擎。刷新只回读原回执，不自动重新写入。

## 4. 原始声明与长期来源

事实更正先由用户直接提交“我的纠正内容”，可直接生成审核，也可“选择目标，交给 AI”后在对话中提出请求。原始纠正声明的 Turn 与后续模型提案 Turn 分别保留，不能把模型总结当原始声明。后者已通过四类真实 Host/Facade/Gateway 与受控 Hermes 事件投影集成，完整 Scripted 浏览器回合仍未认证。Host 先将原始值保存为真实 role=user 消息，再由 Repository 从实际消息读取内容；模型不能调用该直接提交入口来制造用户来源。

实际消息存储于既有 agentMessages 表，Session 只保存元数据；源记录再次核对消息的 Session、Turn、Message、role、原文与时间。对完整原文 UTF-8 计算 SHA-256，并在既有 appMeta 保存独立来源记录。提案绑定原值、新值和该原始来源，模型总结不能替代它。

来源分类严格区分：

- 原条目的已确认 Profile 证据仍由可信层解析，保留原引用；它不自动证明新纠正值。
- 新纠正值标记为 **用户自述、未经独立核验**。确认只授权写入当前简历；不将其变成 Profile 已确认事实。
- 本版不提供外部材料的独立核验或模型自行推断事实的正式写入入口。
- 界面与历史查询均展示原始声明、来源/Turn/Message、SHA-256、原值/新值、确认时间和最终 Revision。

已提交提案、消费后的事实确认与权威 Revision 关联审计保留在 appMeta；查询路径是 `Revision.operationId → precise-audit:<operationKey>`，再核对原始来源与消费记录。TaskState 被下一任务替换或 Session/消息被正式删除后，历史来源仍可读取；前者已真实浏览器验证，后者有实际 Repository 集成断言。原始消息不存在时不能首次提交。

对用户自述运行现有 Fact Guard，并以严格字段/来源校验约束授权范围；不走原本禁止 title/date 的 tailoring rewrite allow-list，也不修改其保护逻辑。原始声明与建议值必须完全一致；任意自由叙事提取、外部真实性认证不在本次已认证能力中。

## 5. 真实事务与恢复证据

A1 专用提交边界复用原 createResumeRevision，一次 Dexie rw 事务覆盖：profiles、jobDescriptions、resumeBranches、resumeRevisions、resumeBranchOperations、agentSessions、agentMessages、appMeta。WebCrypto 在事务外完成；事务内只做同步校验与已声明表的 IndexedDB 操作。

不是仅凭文档声称原子性：实际 appMeta updating hook 观察到上述 8 张表属于当前消费事务，证据在 [实际事务](../quality/ux-01.3-a2-logs/formal-snapshots/actual-dexie-transaction.json)。确认消费失败、Revision put 失败、审计写入失败的 before/failed/afterRetry 快照均保留；失败状态与 before 深相等，重试恰好新增一条 Revision。

其他已验证边界：四类操作并发确认只产生一条 Revision；同 operationId 不同 hash 拒绝；中间正式编辑使旧提案 stale；提交后 TaskState 保存确实抛错仍可恢复原回执；后续有新版本仍可读历史回执；迟到回执不替换其他前台 Session；未确认/拒绝零正式写；原 Profile、非目标分支及历史 Revision 保持相等。

对事实更正后继续删除/排序的条目，仅同步派生正文对应的确认 Hash，保留原确认时间、来源和事实引用。否则既有 renderer 会以 resume_only_confirmation_mismatch 拒绝呈现；新增连续操作回归明确检查可呈现性。

既有 Session hydration 会刷新两处人物索引管理时间戳，拒绝场景原失败快照已保留。测试仅对这两处已定位的时间戳作显式预期，其身份、内容及所有来源/确认仍完整深比较；不把既有读取管理时间戳当成 Profile 事实变化，也未顺便重写该旧机制。
