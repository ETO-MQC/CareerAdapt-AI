# P5.2.0-B Career Domain Independence & Persistence Architecture

Date: 2026-11-01. **PARTIAL / BLOCKED for completion and formal page migration.**

## Decision and scope

CareerAdapt owns the Career Domain Service and storage. Hermes Core owns agent execution, not Career data. Choose a separately owned sidecar with a narrow brokered IPC client. Keep the canonical WorkspaceRepository business rules; introduce a persistence port beneath those rules before enabling service writes. This is an architecture decision plus an isolated migration spike, not a production cutover.

The target production engine preference is SQLite with one service writer, atomic multi-entity transactions and backups. Its runtime/package selection is conditional, not approved for shipment. The implemented temporary target is an immutable file snapshot, deliberately unsuitable for production mutable workloads. No production dependency, Dexie table, runtime, plugin, schema, guard threshold or product source was changed. No user data was opened, copied or exported. No commit, push, installer or subsequent stage.

### Backup, origin and file findings

`exportWorkspaceJson()` at Repository line 7541 is `stage-e-e1-v1`, reads collections sequentially without a single read transaction, omits agentSessions/agentMessages and all five V4 stores, and filters invalid Application rows. It is not a full-fidelity v11 backup. Repository restore-named methods restore entities/revisions/lifecycle, not a verified inverse of a full workspace backup. Source search found no complete matching `importWorkspace`/`restoreWorkspace` entry point; this is not evidence for OS-level backup coverage.

Main persists the preferred port in userData/runtime-ports.json but can select another available port. IndexedDB is bound to scheme/host/port and Electron session partition. A different localhost port or origin yields a different visible database, even if its name is CareerAdaptDb. Persistence of the port reduces changes but cannot establish stable data ownership. Copying Chromium IndexedDB files to another origin is not this migration strategy.

Hermes Renderer and CareerAdapt Renderer do not share authority merely by both being Electron. A plugin runs in Hermes's trusted UI context; its JS import allowlist is not a sandbox. Origin and browser partition changes must be handled by an explicit old-origin read-only bridge followed by a user-reviewed cutover.

## Alternatives

| Criterion | A Main + IPC | B owned sidecar + brokered IPC | C loopback service | D IndexedDB adapter transition |
| --- | --- | --- | --- | --- |
| Lifecycle | tied to shell main | separate domain ownership/process, supervised | independently hosted if supervised | renderer/session lifetime |
| Durable ownership | stable userData path possible | stable CareerAdapt data root outside Hermes releases | stable data root possible | browser profile/partition/origin |
| Hermes upgrades | main integration needs review | versioned protocol compatibility | protocol compatibility | origin/profile changes fragile |
| Renderer origin | IPC boundary removes storage origin | no storage origin dependency | transport origin policy required | remains origin dependent |
| Transaction/CAS | engine transaction required | single writer + engine transaction | service transaction required | current Dexie guarantees reusable |
| Repository cost | high persistence-port refactor | same high refactor plus protocol | same plus server/auth | lowest initial cost, not independence |
| Backup/restore | main-owned job | service-owned checkpoint/backup and replay | service-owned backup | incomplete current JSON export |
| Process crash | main crash takes UI/service | sidecar restart independently | service restart independently | renderer recovery only |
| Concurrent writes | main serialize + CAS | one authority; CAS + receipts in transaction | same; multiple clients need auth/scope | browser transactions, local lock insufficient alone |
| Local security | narrow IPC, sender validation | inherited pipe/Windows ACL + broker | token, peer/origin, CSRF and DNS-rebinding control | browser trust + no Node DB access |
| Windows package | fewer executables, Electron ABI | owned runtime/protocol/update/recovery burden | same plus port/firewall burden | simplest but preserves origin risk |
| Development complexity | medium-high | high | high | low initially |
| Long-term maintenance | shell coupled | best ownership isolation, explicit protocol | additional network attack surface | ongoing origin/migration debt |

B is selected for ownership and upgrade isolation. A is the transport broker, not the business authority. C is unnecessary for a first-party desktop integration and is not implemented. D is permitted only for explicit read-only export and as the pre-cutover source; no dual writes.

### Engine and runtime assessment

Developer executable actually reports Node v24.15.0 and built-in SQLite 3.51.3 (in-memory probe `node -e` using node:sqlite). This proves local availability only. Declared minimum Node 20.9.0 does not establish built-in SQLite availability, and neither Electron's exact embedded Node nor its node:sqlite availability has been verified here. Do not select a library solely from a semver range or build a native addon against the wrong Electron ABI.

SQLite is preferred for multi-entity atomicity, unique receipt constraints, transactional CAS, backup/checkpoint and crash recovery. Choices before production: independently ship and maintain a supported Node runtime with a verified SQLite implementation, or justify an approved dependency/native module with actual Windows packaging tests. No such dependency was installed. WAL/foreign keys/busy handling/backups and power-loss recovery need real engine evidence; none are claimed by the snapshot spike.

The file snapshot target uses exclusive staging writes and atomic same-filesystem hard-link publication. Existing target is never overwritten. It rejects different content or migration identity, accepts identical replay, and leaves failed staging artifacts for diagnosis. No automatic deletion. This tests package transfer/idempotency and independent process readback; it is not a mutable database, a production durability design or a power-loss guarantee. No fsync-based durability claim.

## Domain API and persistence port design

`poc/career-domain-persistence/client.ts` defines the typed client and strict envelope schemas. It is a contract spike, not a connected plugin client. Read families: Profile, facts, jobs, branches, revisions, applications and active context. Future responses must be individually validated/projected, scoped to person/Profile/branch and versioned; facts need a dedicated DTO (the current union is preliminary). No raw rows, SQL, appMeta enumeration, credentials or arbitrary Repository method names may cross it.

Validated action families are intake, reconciliation, import, job parsing, branch creation, tailoring, confirmation, revision creation and export. The spike only accepts operation/profile/revision/proposal identifiers and **rejects every action as unimplemented**. A proposalId is not confirmation. Production request schemas must be discriminated per operation, bind person/Profile/Job/branch, session/source-turn, expected revision and source hashes, and resolve server-held proposals and single-use confirmation receipts. Unknown keys/operations and raw CRUD are rejected. Permanent deletion is absent.

The service command order must be: authorize capability/scope → parse exact action → read proposal and evidence → verify ownership, maturity, Claim Safety and Fact Guard → consume user confirmation where required → execute canonical Repository transaction with CAS and operation receipt → validate projected result. No unconfirmed fact may reach preview/PDF. Profile reconciliation requires explicit Profile consent, distinct from resume-only confirmation. ResumeDocument remains derived. General and job branches remain isolated.

Refactor plan (design only): extract a typed unit-of-work persistence port from the **same** Repository implementation. Explicitly model key/compound queries, stable ordering, uniqueness, transaction table sets and read/write behavior. Implement a Dexie adapter and run current invariants against it before introducing a SQLite adapter. Move process-local serialization into the service command scheduler while retaining engine-level CAS and receipt uniqueness. Port every transaction atomically, including metadata receipts. Do not clone a parallel Repository or create a permissive fake CRUD implementation. A JavaScript promise lock does not replace a DB transaction.

## Authentication and trust design

Hermes Core: runtime. Desktop Plugin: trusted first-party UI, not sandboxed. Agent Plugin: workflow instructions/tool entry points. MCP: transport/tool protocol. Career Domain Service: validation and sole write authority. Persistence: service-private durable data.

Proposed Windows deployment uses a per-user named pipe with user/service ACL, or an inherited private pipe with a nonce handshake. The supervisor owns process launch and pipe handles; service verifies protocol version and per-launch capability. Renderer calls narrow preload methods; main validates the current expected webContents/frame and exact method, and never exposes pipe handles, service bearer secrets or provider credentials to plugin code. Service checks scope, operation receipts and revisions on every command. Process exit revokes per-launch capability; restart reopens the same data root and reconciles outstanding operation IDs before accepting retry. Independent of Hermes agent process restarts; supervisor ownership must be defined outside plugin lifecycle.

If a future loopback transport is chosen: bind loopback explicitly, require per-launch authentication held by broker, strict method/content-type/size/origin/Host handling and no cookie-based authority. Random ports are discovery, not authentication; Origin alone is not authentication either. No such server is exposed by this prototype.

A compromised trusted renderer can still invoke capabilities granted to it and may forge UI intent unless the confirmation channel is separately protected. A compromised main/service or same-user account may access local data. Import allowlists and tokens do not make those compromises safe. These are residual risks, not a claim of a plugin sandbox.

## Migration implementation and evidence

`migration.ts` accepts only an already-open `p520b-fixture-*` CareerAdaptDb at v11. One Dexie `r` transaction enumerates all 28 tables. It records export version, migration ID, schema version, key paths, counts, IDs, canonical per-row SHA-256 hashes and unchanged row payloads. No repair, migration-upgrade callback or business read method is used during export. Tests seed isolated synthetic databases with the existing Repository and domain constructors; export itself is read-only.

The tagged codec preserves explicit undefined, Uint8Array attachment bytes, ArrayBuffer, Date, arrays and ordinary objects without user-content tag collisions. Other types fail closed; Blob/File, exotic structured-clone types, negative zero/nonfinite numbers, cycles and very large payload handling are not certified. Initial spike rejected undefined/binary; after observing production attachment storage, an explicit codec was implemented and tested. No silent stringify fallback remains.

The deterministic fixture includes a Profile, general branch/revision, saved job, job branch/revision, Application and attachment bytes via saveAttachmentSource. Fake Date and deterministic test-only nanoid isolate fixture IDs/times; normal production generators are unchanged. Empty tables are exported and checked but their entity/reference semantics are not thereby tested.

Verification rejects missing table inventories, wrong primary keys, duplicate/missing entity keys, hash/count mismatch, missing branch/Profile/Job/current/source revision, revision predecessor/order/owner errors, Application selections, message session and selected material attachment references. External filePath is rejected rather than read from arbitrary filesystem paths. Embedded bytes participate in hashes. Complete nested fact/evidence, appMeta namespaces, V4 graph, ownership equivalence across all reference families, file discovery/copy and production row-schema validation remain open. This is **not** a production package acceptance validator or a cryptographic signature/authentication mechanism.

Two newly spawned Node readback workers independently decode and verify the published snapshot. This proves process-independent readback, not Domain Service restart, Renderer restart or Hermes Host restart. Fake IndexedDB tests prove the export algorithm, not an actual old-origin renderer bridge. Those distinctions are encoded in machine evidence.

## Faults, rollback and acceptance

| Requirement | Actual result |
| --- | --- |
| Full table manifest / row hashes/count parity | PASS for synthetic fixture, including binary bytes and optional values |
| Duplicate migration / concurrent same package import | PASS, one published target and matching idempotent replay |
| Conflicting migration/content | rejected without replacing target |
| Failure after staging, before publication | PASS; no target visible; retry safe; staging retained |
| Hash corruption / missing revision / attachment | rejected; corrupt persisted readback rejected |
| Repository concurrent revision/CAS | PASS in original Dexie Repository, one winner/one RevisionConflictError; target service writes unimplemented |
| Independent worker process restart/readback | PASS, two fresh processes |
| Real Domain Service / Renderer / Hermes Host restart | NOT EXECUTED; no connected service exists |
| Rollback retaining post-migration new writes | **BLOCKED**, explicit rollbackAfterWrites rejection |
| Full legacy browser bridge / complete reference and file integrity | PARTIAL; fake IndexedDB and bounded reference validator only |
| Plugin validated production writes | BLOCKED; API spike denies them all |

Rollback must not switch back to the old export after new service writes. Required protocol: fence new commands, drain transaction queue, produce a final checkpoint plus complete ordered post-cutover journal with stable operation IDs/versions/evidence/bytes, replay through canonical reverse adapter to a **new isolated** legacy-compatible database, validate hash/count/reference/receipt parity, then atomically change authority. Preserve old and new snapshots/journal until user acceptance; if replay is unsupported, retain the service data and refuse rollback/cutover. No dual writer or discarded new revisions. This protocol is not implemented or tested; old-source existence alone is not rollback success. The test asserts explicit BLOCKED, not a rollback PASS.

Thus **P5.2.0-B is PARTIAL; completion and formal page migration are BLOCKED**. No P5.2.0-C, FINAL GO, P5.2.1 or page migration is authorized by this result. The remaining work belongs to this B contract and requires review, not an automatic next stage.
