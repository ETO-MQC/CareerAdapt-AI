# P4.8a Career Resume Intelligence & Competitive Matching

Date: 2026-09-10

## Decision

P4.8a extends the existing CareerProfile confirmed-fact ledger, Resume Schema
v2, ResumeBranch/ResumeRevision lineage, Profile Write Contract, and canonical
Tailoring chain. It does not add a second career database, Agent, runtime
router, Dexie table, template family, or writer architecture.

The key product change is to make evidence maturity explicit without making
user-confirmed capability depend on project provenance:

| maturity | meaning | safe resume posture |
| --- | --- | --- |
| `demonstrated` | A fact is supported by a concrete project, work, study, or other demonstrated asset. | Describe the demonstrated action, method, ownership, and result when present. |
| `confirmed_capability` | The user explicitly confirms the capability, but no demonstrated asset is required. | Use bounded capability wording or a skill entry; do not add ownership, scale, metrics, or professional experience. |
| `familiar` | The user reports exposure or basic familiarity. | Use `了解`/`接触过`-level wording only, and keep it out of core claims when it would mislead. |
| `learning` | The user is learning or only aspires to use it. | Normally keep it in a learning/current-study context, not as a current core competence. |

The existing `confirmedByUser`, provenance, risk, and source references remain
authoritative. `maturity` is a semantic qualifier, not a replacement for
confirmation or Fact Guard. Legacy facts remain readable through a
deterministic compatibility default and are not silently upgraded by a new
claim.

## Existing architecture audit

- `CareerProfile.experiences[].facts`, `skills[].fact`, and
  `certificates[].fact` already provide a single confirmed ledger with
  provenance; `structuredFacts` is the synchronized Resume Schema v2
  projection.
- Resume content already carries `factRefs`, source excerpts, guard snapshots,
  and explicit `resume_only` confirmation. Manual edits therefore have a safe
  scope boundary and do not need a new write path.
- P4.6b already separates hard factual protection from confirmable claims in
  the tailoring chain, but evidence units currently collapse mature facts and
  user declarations too aggressively for competitive matching.
- Profile intake already computes asset completeness and information gain and
  asks one bounded question at a time. P4.8a will make its useful experience
  dimensions explicit and add a compact factual review before commit.
- General Resume composition already builds an Evidence Graph, Blueprint,
  Reviewer, and immutable checkpoint. It needs maturity-aware ranking and
  stronger anti-boilerplate review, not a new composer.

## Reference comparison and adopted lessons

### Industry Resume Toolkit — methodology only

Source: [industry-resume-toolkit](https://github.com/shangsitongshizaitiantang/industry-resume-toolkit)
(`CC BY-NC-ND 4.0`; reference only, no source text, prompt, pattern file, or
derivative content is copied).

The toolkit distinguishes information hygiene, business-value translation, and
experience mining; it also separates “create/rebuild” from “improve an already
complete resume” and uses iterative questions that skip information already
available. CareerAdapt adopts those as independent product rules: remove weak
filler, translate a supported action into business-relevant language, mine one
experience progressively, and keep review/update different from first
composition.

### Reactive Resume — architecture and template boundary

Sources: [project architecture](https://docs.rxresu.me/contributing/architecture),
[template guide](https://docs.rxresu.me/guides/choosing-a-template), and
[export guide](https://docs.rxresu.me/guides/exporting-your-resume). Reactive
Resume is MIT licensed.

The useful pattern is a typed resume schema/content model separated from PDF
templates and rendering packages, with proposal/review controls for AI edits
and stale-proposal handling. CareerAdapt already has the corresponding
Profile → Evidence Graph → ResumeRevision → render/export boundary. P4.8a
strengthens content quality and provenance only; template/render candidates are
deferred to P4.8b.

### OpenResume — portable content model

Source: [OpenResume specification](https://github.com/TheOpenResumeProject/OpenResume)
(`schema.json`, project license applies).

OpenResume separates a structured resume data object from formatting and
supports predictable sections plus lightweight metadata for searching and
categorization. CareerAdapt adopts the principle, not the schema: Resume
Schema v2 remains the domain contract, Profile facts remain upstream memory,
and presentation/template data remains downstream.

## Product decisions

1. Keep one Profile fact ledger and one canonical Tailoring chain.
2. Represent demonstrated, confirmed capability, familiar, and learning
   explicitly in existing fact/provenance and evidence bundles.
3. Treat hard identity, organization, school, credential, date, role,
   ownership, exact metrics, denials, and contradictions as deterministic
   blockers. Treat user declaration, limited familiarity, weak evidence, and
   resume-only wording as reviewable soft warnings.
4. Productize legacy intensity values as `STEADY` (conservative),
   `COMPETITIVE` (balanced/default), and `MAX-FIT` (proactive). Mode changes
   selection and questioning effort, never truth standards.
5. Max-FIT may ask at most three high-value capability questions per tailoring
   task, one at a time, using demonstrated / basic independent / familiar /
   not used choices. Answers stay resume-only unless the user explicitly asks
   to sync them through the existing Profile Write Contract.
6. Experience mining captures identity, context, contribution, action,
   method/tool, difficulty/decision, deliverable, result/verification, and
   known scale progressively. A compact factual review precedes commit; three
   to four reusable fact bullets is a target only when evidence supports it.
7. General Resume chooses broad, strong facts rather than one-JD coverage.
   Review proposes meaningful diffs and does not rewrite everything by default.
8. Future private resume-corpus support is documented as an import/evaluation
   interface only. P4.8a does not train, fine-tune, embed, or distribute
   source resumes.
9. Historical E2E tests will be classified as current, superseded and covered,
   obsolete product contracts, or real-provider-only. Canonical current
   journeys are the acceptance surface.

## Deferred to P4.8b

New templates, template marketplace work, renderer architecture changes, and
corpus-driven style learning are explicitly deferred. The next useful
template work should start from a permissively licensed, content-independent
template/render boundary such as the Reactive Resume pattern.

## Runtime boundary

P4.8a changes Career Skills, Profile intake/mining policy, maturity-aware
evidence and quality policy, Tailoring mode/gap policy, and deterministic
domain tests/evals. Hermes Runtime Core, Supervisor, AgentRuntimeRouter, MCP
transport, auth, SSE, reattach, lifecycle, and process topology are frozen.
