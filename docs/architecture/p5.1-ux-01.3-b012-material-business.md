## 1. 原链路、缺口与本次链路

沿用 Resume Center / Hermes → AgentAttachmentStore → MaterialIntakeService → ResumeImportOrchestrator → SourceDocument v2 / 既有 OCR / 经过能力判断的 Vision → 既有 Mapper → ImportedResumeDraft → ResumeImportWizard → ProfileReconciliationEngine → confirmImportedResume → WorkspaceRepository。

修改前的实际缺口：

- canonical draft 只含文件与文本 hash，目标/用途改变可能返回另一个 Profile 的已保存结果。
- 已有 Profile 尚无通用简历时，即使明确传 `createGeneralResume:false`，Repository 仍可能创建 Branch / Revision。
- 中心入口 Session/任务定位仅在组件内存；人工转写与恢复期间的目标信息不能完整恢复。
- 来源 UI 只有页文本，无法在同处查看原附件、hash、引擎、bbox、置信度与原始来源块。
- 非简历材料没有被既有局部规则映射时，只剩无法采用的未分类文本；改栏目只改标签，未改变 canonical item。
- 单一字段的“拒绝”原本仅改候选元数据，原投影值仍可能被材料提交使用。
- 中心容器既有 `.resume-create-panel .section-heading { display:none }` 隐藏了审核分类选择器。计算样式诊断保存在 `manual-layout/.../classification-layout.json`。

最终链路仍使用同一服务/草稿/对账引擎。材料按原文件、目标种类/ID、新人物意图和用途定位；已确认的新人物材料只在权威 Profile ID 相同时复用回执。每个 Session 必须先 restore 自己的确切 attachmentId；hash 只参与去重。用户编辑/拒绝/分类只改 provisional draft，正式确认才执行原事务。
