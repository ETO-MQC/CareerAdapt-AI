# 统一工作台信息架构

2026-11-04。目标品牌：**CareerAdapt AI — Powered by Hermes**。

## 唯一物理全局菜单

AI工作台（Hermes新建对话/最近会话/历史）→职业管理（首页/Profile/Jobs/Applications/Resume Studio）→资料导入→设置（Career分类+原生Hermes设置职责）。只有一个Host Sidebar。Profile分类为页内横向Tabs；岗位/申请Tabs与Studio板块树不是全局菜单。会话列表仍归Hermes，不复制Session存储或聊天实现。

当前三个菜单来自：Hermes Sidebar + P522 CareerExperience的职业入口列 + Profile分类列。各列局部职责不同，却造成并列全高度导航。恢复路径是把所有Career入口贡献到Host现有Sidebar、移除业务route内的全局入口列、把Profile分类移为Tabs；不复制旧AppShell，不以CSS隐藏Host。

## 锁定 SDK 结论

源码：`apps/desktop/src/app/routes.ts` 的 `SIDEBAR_NAV_AREA` / `SidebarNavContribution`；`src/sdk/index.ts`导出；`src/app/chat/sidebar/index.tsx:262,1105`合并 `[...SIDEBAR_NAV,...contributedNav]`。route为workspace全页，不是Chat子插槽。贡献payload只有codicon/label/path；贡献外层order经`contrib/registry.ts:67`排序。

| 需求 | 结论 |
|---|---|
| 六个Career业务入口都放Host Sidebar | 公开接口可逐个贡献，保留原生会话入口；源码支持，本轮未安装六入口正式插件 |
| 保留新建对话和历史 | 支持，原生sidebar仍渲染；不替换SIDEBAR_NAV |
| 排序 | order可控制贡献间顺序；不能据此承诺任意穿插或重排Host内建入口 |
| 自定义分组 | SidebarNavContribution没有group/section/children；目标分组尚不由此契约支持 |
| 唯一物理全局导航 | 方案A无需Core即可通过平铺贡献实现；目标品牌分组版还需最小扩展 |
| 不同业务route保持导航 | Host管理同一sidebar，业务页面不再创建自己的全局导航；完整迁移需另验收 |

## A / B / C 方案

- **A：现有公开SDK平铺入口**。最小风险，保持Host内建菜单和Sessions，在其下追加Career业务项。可以一个物理主菜单，但还达不到目标分组/品牌编排。推荐后续验证起点。
- **B：用户另行授权的最小Host扩展**。公开typed nav section/group、order与builtin grouping policy，保证原生会话/设置/键盘功能不可静默丢失；再实现目标IA。建议最终方向，不在本轮修改Core。
- **C：完整自定义Host Shell**。控制面最大，但升级与原生能力维护成本最高；不能作为本轮默认路线，也不能用隐藏Host Sidebar来模拟。

## 工作台与专业页面

AI页：左侧唯一导航，中间Hermes原生Chat（消息、流式、附件、Tool Activity、Stop/Retry、生命周期由Host负责），右侧Career Artifact。输入区留在Chat布局流内，不跨越全局菜单或覆盖Artifact。独立原型只展示静态Chat，不能称原生集成成功。

Artifact默认40%，34–50%调节，键盘/指针分隔、折叠恢复、独立滚动、任务选择及错误隔离；窄于800使用可关闭覆盖层，桌面1024仍保留并排。正式Host Pane需同时验证最小宽度和可访问性，不能套用原型PASS。

业务页：中间完整Profile/Jobs/Applications；Profile保留条目列表和详情编辑，分类转横向；Jobs保留来源/核对/要求/匹配/分支流程；Applications保留看板/列表/材料/时间线。局部动作不能当全局导航。

Studio：独立route、左板块/条目、中A4编辑与预览、右排版/样式/页面、上方保存/撤销/模板/导出。保留TipTap和正式renderer，不缩为Chat Markdown或Artifact卡片；保持ResumeDocument派生、Branch/Revision与presentation职责分离。

## Pane 技术判断

公开 `PANES_AREA` 确认存在。`tree/store.ts:840–875`会静默adopt新pane，`insertAtGroup(...,false)`不强制front；显示还受active tab、hiddenTreePanes、collapsed、dismissed、side/zone状态影响。`controller.tsx`明确boot-hidden panes可能挂在display:none后。此机制解释了“挂载不等于可见”的可能性，**不能确定旧失败现场的唯一原因**。

内部`revealTreePane/setTreePaneHidden/dockPaneBeside`存在，不等于插件公开稳定API；SDK没有已证明的同等级typed reveal/restore/任务绑定契约。本轮先定位实际sidebar源码，未重跑旧两个Pane测试，真实并排仍NOT VERIFIED。宽度/独立滚动/恢复/任务状态/生命周期只有原型验证；贡献disposer UI清理不等于权限撤回。

最小建议：公开PaneContribution类型、reveal/collapse/restore/queryVisible、Host持久宽度和minWidth契约、可聚焦Sash与方向/Home/End/ARIA数值、session/task/artifact/revision只读绑定及晚到隔离。先证明现有可访问入口，再另授权一次有界真实Pane验证；必要时才改Host。当前不修改Core、不调内部store、不注入Host DOM。
