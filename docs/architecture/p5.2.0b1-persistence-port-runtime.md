## Actual canonical call chain and transaction contract

`editResumeBranch` / `editResumeBranchBasics` → `WorkspaceRepository.mutateResumeBranch` → `CareerPersistencePort.withBranchMutation` → `DexieCareerPersistenceAdapter` → original five-store rw transaction → operationId replay lookup → Branch load/schema/lifecycle/migration/current-revision/reference checks → expectedRevision CAS → Profile and optional Job exact-ID reads → source checks/schema parsing → canonical existing mutation callback/Fact Guard or explicit resume-only confirmation → re-read Profile → increment Branch revision and derive sync status → create linked Revision → Branch put → Revision put → operation receipt put → atomic commit.

Replay still precedes CAS; same operation replay with stale expectedRevision returns existing persisted Branch/Revision without writes. Validation failures and storage errors propagate unchanged. No new auth layer was invented: this remains trusted internal Repository infrastructure with existing Profile/Job reference semantics, not a plugin security boundary. A pre-existing cross-target operationId behavior is preserved rather than silently changed into new business semantics.

| Concern | Contract preserved |
| --- | --- |
| Read stores | resumeBranches, resumeRevisions, resumeBranchOperations, profiles, jobDescriptions |
| Canonical writes | Branch, linked Revision, BranchOperation receipt; legacy sync callbacks may also write profiles in the same existing transaction |
| Keys/query | Branch/Profile/Job/Revision primary ID; operationId indexed exact lookup, existing unique index |
| CAS | Compare loaded branch.revision with expectedRevision inside serialized rw transaction; increment exactly once; conflict remains RevisionConflictError |
| Ordering | Replay before lifecycle/CAS; mutation then fresh Profile read, sync calculation, Revision creation, Branch→Revision→receipt writes |
| Revision linkage | revisionNumber follows existing Branch revision (initial 0); previousRevisionId is prior currentRevisionId; restoredFrom preserved |
| Atomicity | All five stores enlisted before any read; no split writes, swallowed failures or external IO |
| Composite indexes | None used in this selected editing transaction. Creation/draft paths use [profileId+jobId] and remain outside this slice |
| History sorting | Existing listResumeRevisions uses numeric revisionNumber ascending, not Dexie cursor/insertion order; unchanged |
| appMeta | Not part of this transaction. Branch receipts are resumeBranchOperations; creation presentation config and other receipts remain separate existing appMeta transactions |

The transaction wrapper must itself be async. Initial non-async wrapping caused Dexie's async-zone detection to report PrematureCommitError in two Profile sync tests. Restoring async restored the original 30 tests; no timeout extension, keepalive hack or weakened assertion. This framework-specific requirement belongs only in the adapter.

## Port design and migration boundary

`careerPersistencePort.ts` defines a bounded BranchMutationUnitOfWork: typed Profile/Job/Branch/Revision reads, indexed operation lookup, typed Branch/Revision/receipt saves, and one transaction callback. It imports domain types only. It does not expose tables, Dexie promises, CRUD dispatch, transactions or storage access through DomainRead/DomainAction/Plugin APIs. Adapter contains storage operations only; every rule remains in the same WorkspaceRepository. Constructor's public signature is unchanged; default adapter uses the original CareerAdaptDb singleton or supplied test DB. DB schema remains v11 with 28 stores.

Fully traversed first portable business entrypoints are `editResumeBranch` and `editResumeBranchBasics`: both mutation callbacks are free of Dexie operations. The shared mutation engine is now behind the port for all its callers (machine evidence lists them), but this does **not** mean all callbacks are migrated. Profile sync callbacks still call putProfileInTransaction, restore/undo still directly read Dexie, and other methods still use the concrete DB. Existing outer transactions compose with the same ambient Dexie scope. They continue to work but cannot be routed to a future SQLite adapter as-is. The Repository itself still imports/constructs Dexie infrastructure and cannot yet serve as an independent Node service.

Not migrated: General/Job creation including appMeta presentation writes, draft-to-branch creation, Profile write/version/metadata transactions, Job persistence, reconciliation, artifact receipts, binary metadata, export/application workflows, revision list/query APIs, and all other direct Repository persistence. These retain their current implementation and rules. No fake SQLite-shaped Dexie facade and no second Repository were created. Generic binary operations are intentionally not invented for a branch-edit slice that does not access binary data.

## SQLite feasibility for this slice

A future adapter can implement the same typed unit using one connection and BEGIN IMMEDIATE/COMMIT/ROLLBACK. Primary IDs map to exact keyed SELECT; operationId maps to a UNIQUE indexed column with binary/case-sensitive equality, preserving first-result behavior under uniqueness. Insert/update order must stay Branch→Revision→receipt; do not add an immediate currentRevisionId foreign key that rejects the existing Branch-before-Revision sequence (deferred constraints are an option). Preserve existing put/upsert semantics; appendRevision names the domain operation, not a new uniqueness policy.

CAS must read and compare inside the same write transaction or use an UPDATE WHERE revision=expected with affected-row validation. A busy error is not a CAS error: define a bounded contention policy later, never silently bypass CAS or auto-replay business mutations. Rollback the entire unit on any failure including a receipt write. Distinct adapters must not double-write.

For later draft queries, [profileId+jobId] maps to a composite SQL index with identical equality. History ORDER BY CAST/revisionNumber numeric ascending must preserve the existing stable tie behavior if ties are possible; no untested insertion-order assumption. Optional jobId and absent properties must retain undefined-vs-null semantics in the payload codec; indexed absent values must not accidentally match empty strings/SQL NULL. Use explicit binary collation and deterministic ordering where the application specifies it. These later mappings are plans, not implemented adapters.

appMeta remains heterogeneous: binary attachment values need a tagged codec/BLOB metadata table-column design that retains Uint8Array/undefined and hashes, as demonstrated in B's codec; never plain JSON stringify. appMeta business receipts must enter their original enclosing transaction when those paths are ported. No new Dexie tables or binary API is introduced here. Legacy callbacks depending on ambient Dexie must be migrated before selecting a non-Dexie adapter for them.
