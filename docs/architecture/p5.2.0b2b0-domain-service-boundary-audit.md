## 6. Domain API / IPC v1 契约（设计，未接入）

所有请求严格 discriminated Schema，拒绝未知键和operation，不反射调用Repository。统一 envelope：`apiVersion:1, requestId, method, scope:{workspaceId,personId,profileId}, expectedServiceEpoch, deadlineAt, payload`。身份/允许scope由broker鉴权绑定，不能仅信请求中的ID。write另有持久 operationId、expectedRevision、expectedRevisionId、proposalId/confirmationReceiptId（需要时）；create用已验证的来源Profile revision/hash，目标不存在，无伪造expectedRevision=0。协议外的workspaceId是authority scope，不新增正文Schema字段或Dexie表。

| method | payload与结果 | 对应canonical行为 |
|---|---|---|
| hello | supportedApiVersions、clientBuild → selectedVersion/serviceEpoch/schemaVersion/capabilities | 不兼容fail closed，暴露capability仅表示明确已实现 |
| profile.get / job.get | entityId → scoped Schema投影与source revision/hash | getProfile/getJobDescription |
| branch.get / branch.list | branchId或purpose/cursor/limit → DTO列表及读版本 | get/listResumeBranches；强制scope，不支持任意filter |
| revision.get / revision.list | branchId/revisionId或cursor/limit → scoped历史 | get/listResumeRevisions |
| branch.createGeneral | name、includeProfileFacts/Basics、selectedCanonicalItemIds、sourceProfileRevision/hash、operationId | createGeneralResumeBranch；composition服务端派生，不接受任意ResumeJSON |
| branch.proposeEdit / branch.proposeBasics | branchId、expected版本、typed item/field patch、AI来源证据 → proposalId/diff/hash/requiredConsent | 只创建待审核建议，不改变正式Branch |
| proposal.confirm | proposalId、proposalHash、scope、user gesture challenge → 单次receipt | broker可信确认入口；会话/来源/目标/版本绑定 |
| branch.applyProposal | proposalId、receiptId、expected版本、operationId → branch/revision/receipt | editResumeBranch或editResumeBranchBasics；内部才映射resume-only确认 |
| branch.restore / branch.undo | branchId、目标revisionId（restore）、expected版本、operationId、明确确认 | restoreResumeRevision/undoResumeBranch，创建新Revision，不倒退revision计数 |
| operation.getStatus | operationId → committed/resultRef、pending、notFound或unknown | 仅返回同scope receipt，不以超时推断未提交 |
| request.cancel | requestId → cancelledBeforeStart、tooLate或unknown | 不撤销已提交业务操作，undo另走新命令 |

只读默认limit50、最高100，payload上限1MiB（附件走独立授权流）、单broker最多32个在途请求，超限RESOURCE_EXHAUSTED；均为待验收设计预算。默认read5s/write15s、hello10s、关闭5s，测试可注入时钟，不以超时自动重试write。持久操作结果不包含秘密或大附件。

响应：`{apiVersion,requestId,serviceEpoch,operationId?,status,result? ,error?:{code,retryable,outcome}}`。outcome区分notStarted/rolledBack/committed/unknown。错误至少：INVALID_REQUEST、UNSUPPORTED_VERSION、FORBIDDEN、NOT_FOUND、REVISION_CONFLICT、OPERATION_ID_REUSE、CONFIRMATION_REQUIRED、CONFIRMATION_STALE、FACT_GUARD_BLOCKED、REFERENCE_INVALID、DEADLINE_EXCEEDED、CANCELLED、SERVICE_RESTARTED、SQLITE_BUSY、DATABASE_CORRUPT、SCHEMA_TOO_NEW、STORAGE_ERROR。禁止回传路径、SQL、个人数据全文或stack给UI，内部日志以request/operation ID关联。

CAS与幂等顺序：先鉴权和ownership，再在同一事务读取operation receipt；同scope、method、canonical payload hash相同才replay（允许旧expectedRevision重试），同ID不同payload/目标拒绝；没有receipt时检查当前branch/currentRevision/source hash、确认及事实规则，原子写Branch/Revision/receipt。**现有Repository receipt replay未绑定完整scope/payload**，不能直接暴露其operationId入口；新Domain receipt设计需在同一事务增加typed metadata，不修改原Schema阈值。本轮未修。

确认不能由不可信Renderer自报。服务持有proposal和精确diff，可信broker显示/核验与hash绑定的用户确认；如锁定Host没有可用独立可信确认表面，生产AI写入仍BLOCKED，不能用SDK完整权限作“用户同意”证明。已有Repository confirmAsResumeOnly只是内部业务参数，服务须验证receipt后才设置，Profile同步必须独立确认。proposal/receipt消费与写入应进入同一UoW；如果现有 appMeta 单独consume无法原子组合，不做consume→write两事务补偿式上线。

迟到响应仅由requestId+epoch定位原请求，不覆盖用户已切换分支；write超时显示结果未知，先operation.getStatus再以同operationId重连。服务重启换epoch使旧传输报文失效，但durable operationId保留；重试旧操作须新requestId/epoch，不能换operationId盲写。服务器deadline前未开始可取消，开始后以事务最终状态为准，客户端Abort不代表rollback。operation receipt存结果Revision引用并可读回，不能只返回当下已被后续编辑改变的Branch来冒充原响应。

## 7. 数据库所有权与生命周期（待实施状态机）

`STOPPED → STARTING → MIGRATING → READY → DRAINING → STOPPED`；异常进入CRASHED/RECOVERING，完整性失败QUARANTINED，版本不支持INCOMPATIBLE。只有READY接新业务。Host启动不等于Domain ready；Agent运行另须原MCP/domain READY，不能因新服务跳过现有门禁。

1. CareerAdapt拥有的外部 supervisor 启动Sidecar，固定只读bundle manifest/entry，不允许Plugin传exe、参数或数据库路径。Hermes Core仅提供Host生命周期，不能把插件register/unmount当服务所有者。锁定SDK尚无已验证的启动/关闭hook，因此独立supervisor与Host的可用extension接入为B2-B1前置验证。
2. 数据根位于CareerAdapt管理的每用户持久目录，脱离release/Hermes checkout/origin，不复用任意Plugin配置路径。库文件名由authority选定；数据库、附件与备份目录均限制当前OS用户。逻辑workspace与person/profile ownership每次复验，不把本机用户身份当Profile授权。
3. 每数据根只准一个服务：supervisor单实例锁+OS级数据根owner lock（随进程释放）+SQLite事务；第二实例在打开写库前拒绝。不能仅创建可能遗留的pid文件；旧PID/同名pipe不等于活owner。具体Windows owner-lock实现须资格验证，锁失败不擅自删除文件。
4. 首选私有继承stdio管道；如需独立broker连接则用每用户ACL命名管道，服务校验per-launch nonce、peer/协议和capability；传输用长度帧+最大长度，stdout只协议、stderr脱敏日志。Python plugin backend到此通道的连接能力必须真实测试。不得将管道secret交Renderer或启动命令行/日志。
5. ready响应包含epoch、DB identity（非路径）、schema/API/capability与完整性结果。迁移完成前不ready；Hello范围没有交集时停止，禁止silent fallback到Dexie或默认另建空库。
6. Host关闭/broker断开：停止接单，5s内drain事务、保存已提交receipt、完成checkpoint/关闭连接、退出；超时终止会产生unknown结果，重启后按operationId对账。supervisor维护父进程/lease，防止Host崩溃留孤儿writer。不能删除WAL/数据库以解除锁。
7. Sidecar异常退出：立即撤销epoch/能力，UI只读并保留未确认patch；监督最多3次/60s（1/2/4s退避），超额FAILED等待显式恢复。完整性失败不反复重启、不静默新建空库。重连先Hello、重新鉴权、逐个核对未知write再开放写入。
8. Host重启丢失内存pending时，服务durable receipt/proposal仍保留；如客户端需自动找回operationId，须typed pending-operation journal（无敏感payload）并定义重放过期策略，未实现前不承诺自动恢复。陈旧epoch报文拒绝，已提交operation只replay。
9. SQLITE_BUSY：只在BEGIN IMMEDIATE之前有限退避（建议总1s且不超过请求deadline），耗尽返回retryable/notStarted；事务开始后不自动重跑业务回调，失败明确rollback。SQLITE_LOCKED与busy分开诊断；commit/rollback异常若无法断言结果返回unknown并关闭连接对账。现有B2-A constructor busy未重试，owner启动锁未实现，不能掩盖。
10. Schema migration由唯一authority、启动READY前、独占维护模式执行；记录版本/校验和，先一致性备份，事务化升级；未知新schema fail closed。B2-A user_version1不是Resume Schema v2或Dexie v11，三者不得混用。禁止旧程序打开新库写入；软件回退依赖可验证兼容或带新写入的反向journal，父B这项仍BLOCKED。
11. 备份使用引擎一致性backup API（或已验证的维护模式快照），连同附件manifest/hash、schema/API/runtime信息校验；不可复制活动sqlite主文件后丢WAL。恢复需要用户明确选备份、离线staging integrity/reference检查、关闭所有连接、备份现库，再由authority原子切换数据根；保留旧库，失败不覆盖。单个Revision restore不等于数据库restore。
12. Domain v1和SDK/backend capability握手做兼容矩阵，Hermes更新先以fixture验证read/write/confirm/restart；不把Hermes版本当Domain schema版本。平台发行需各OS/CPU ACL/pipe、停止、更新和数据保留资格。

WAL是候选配置而非当前PoC已启用能力；生产需选定journal/synchronous政策并验证磁盘满、强杀、checkpoint与backup恢复。SQLite官方说明WAL仍可出现busy，且不能用于跨主机共享文件系统。本机3.51.3已处官方WAL-reset修复版本范围，但这不证明本产品WAL恢复已认证。[WAL说明](https://www.sqlite.org/wal.html)、[一致性备份](https://www.sqlite.org/backup.html)。

## 8. 信任与数据边界

| 层 | 信任责任与限制 |
|---|---|
| Hermes Core | Host/Agent运行生命周期；不持有Career数据业务权威，本轮不改Core |
| Plugin Renderer | 展示/编辑建议；SDK同realm不是安全边界；不得持密钥、DB路径、raw SQL或可信确认权 |
| Host Bridge | 校验会话/来源、operation allowlist、scope、大小/频率，可信确认与通道凭据；SDK现有profile-aware路由仍须Career ownership复验 |
| Career Domain Service | proposal/confirmation、Resume v2、Fact Guard/Claim Safety、生命周期/来源/所有权、CAS、幂等；唯一正式业务写入口 |
| Adapter | codec、事务、唯一receipt、持久化完整性；不作事实推断，不给调用者任意SQL |

插件供应链：固定获准来源及包hash、依赖/构建产物审计；hash只证明字节一致。恶意同realm插件能操作UI/共享Host权限，现有SDK不能保证真实用户点击与插件伪造点击可区分；这是残余高风险，未经可信Host确认设计和验证前不开放AI事实写入。Python后端插件同样是受信任代码而非沙箱，不允许其凭UI传来的路径启动服务/读取文件。

文件/附件：用户选择产生服务端授权opaque handle，限定profile/session、类型/字节数、有效期/hash；不接受filePath任意读，不允许路径穿越/符号链接越界/通过source URL触发任意本地访问。预览/PDF不得包含未确认事实；ResumeDocument继续派生。通用/岗位/其他Profile跨scopeID一律拒绝，即使ID真实存在。

数据库损坏：隔离并保留诊断，停止写入、用户选择经验证备份恢复；不删除库。备份含个人信息，最小权限、明确导出与保留政策，不自动上传；不能宣称SQLite或现有备份默认加密，密钥保护另行设计。恢复不能跨profile偷渡确认或忽略schema compatibility。[Electron官方安全要求](https://www.electronjs.org/docs/latest/tutorial/security)同样要求验证IPC sender；Origin、pluginId和UI禁用按钮均不能单独授权。

## 9. 第一条最小完整业务切片与 B2-B1 执行计划

仅合成fixture：读取Profile/Job → 创建General（Revision0+presentation+receipt）→ 读取Branch/内容 → AI提出typed patch（fixture模拟，非新事实）→ 明确确认精确diff → apply（Revision1）→ 历史查询 → Undo产生Revision2 → Restore指定Revision产生Revision3。验证原Profile/Job、其他General、Job branch、其他person/profile逐字不变。Job专属创建、导入、归档删除、布局编辑、PDF/评分不纳入第一条service闭环。

所需Port增量：scoped ReadPort（Profile/Job/Branch/Revision/branch列表/历史稳定分页）；GeneralCreationUoW（原5实体及typed presentation metadata）；现有BranchMutationUoW让restore/undo回调使用readRevision；typed proposal/confirmation/Domain operation receipt metadata组合事务。只为这些namespace建方法，不暴露任意appMeta或原始CRUD，不新增Dexie表。General creation不需要requirementMatches；岗位创建后续才需Match查询/来源Revision/presentation完整事务。附件fixture只用可验证文本证据；外部bytes未支持时明确拒绝，不能悄悄删引用。

| 顺序 | B2-B1任务（须用户另行批准） | 直接可执行的验收/停止条件 |
|---|---|---|
| 0 | 再核Git/B2-A hashes；确定B1仅fixture设计实现范围 | 保留全部已有修改，发现证据不一致先报告 |
| 1 | 无Core改动SDK/backend broker可行性与可信确认技术验证 | 真实锁定Host ctx.rest route/auth/profile隔离、断连和禁用，合成数据；不能验证则停在BLOCKED，不写生产服务 |
