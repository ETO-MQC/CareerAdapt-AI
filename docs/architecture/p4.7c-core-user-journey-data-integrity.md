# CareerAdapt AI — P4.7c Core User Journey & Profile Data Integrity

Date: 2026-09-05

This note is the P4.7c design record. It freezes the external lessons and the
Profile/Resume authority boundary before implementation. It does not add a
database table or a second runtime/orchestration layer.

## PROFILE_DATA_AUTHORITY_MATRIX

The Profile is one aggregate persisted through `WorkspaceRepository`. The
confirmed fact ledger is the factual authority; `structuredFacts` is the
structured v2 projection of that ledger and the source for the Profile editor.
Both are committed together by the Profile write contract. A structured item
with an unresolved fact reference is invalid for Resume generation and must be
reviewed instead of being silently dropped.

### Write invariant

Every confirmed Profile write must produce a parsed Profile in which:

1. every non-summary `structuredFacts[].factIds` resolves to a confirmed fact
   in the Profile ledger;
2. the structured item fields, editor projection and legacy compatibility
   fields represent the same semantic content;
3. source provenance remains attached to the fact/structured item; and
4. any material source detail that cannot be projected is rejected or marked
   review-required, never silently reduced to a title/date-only item.

Profile-to-Resume synchronization is an explicit diff/revision operation. A
Resume-to-Profile action can propose only a user-confirmed new factual claim;
style, ordering and job-specific wording do not become Profile facts. A
job-specific Resume defaults to `resume_only`.

## Frozen journey risks

The three observed defects are treated as product-contract defects, not model
quality alone:

- Quick Actions are typed Host commands. Import opens the existing composer
  picker before any Hermes/tool call; intake opens an onboarding shell before
  any extraction call.
- `career.workflow.compose_resume` is the only normal model-facing general
  Resume facade. Host-owned Profile identity and revision are injected at the
  gateway boundary, preserving CAS without asking Hermes to guess IDs.
- A Resume import can parse without a Profile. Reconciliation and Profile
  creation happen only after the Import Draft is available and the user has a
  target/confirmation decision.

## Implementation boundary and acceptance evidence

The confirmed Profile write chain is:

`ProfileWorkspace.saveProfileSnapshot` → `WorkspaceRepository.saveProfile` →
`putProfileInTransaction` → `synchronizeProfileStructuredFacts`.

Repository lifecycle operations use the same normalization contract before
returning a Profile. The import confirmation path first preserves the full
structured body (background, tools, descriptions, highlights, outcomes and
research metadata), then the write contract validates ledger references and
rebuilds compatibility projections. The earliest identified rich-detail loss
was the old `structuredBodyText` projection in
`src/domain/resumeImport/confirm.ts`, which retained only a narrow highlights /
description choice before legacy projection and migration.

The rich-lineage golden covers education, work, multiple projects, outcomes,
tools, background and research fields from confirmed Profile through the
general branch and immutable Resume revision readback. The implementation does
not silently repair arbitrary historical records: an explicit recovery or
editor save is required, and malformed unresolved references fail closed.

Telemetry is intentionally bounded by the runtime boundary. A new Hermes run
can report the accepted `/v1/runs` start proxy and bridge-observed tool phases;
it cannot claim the number or duration of Hermes-internal provider calls or
hidden MCP network requests. The deterministic acceptance suite therefore
checks semantic trajectory, persistence and UI behavior without hard internet
CI or real provider credentials.
