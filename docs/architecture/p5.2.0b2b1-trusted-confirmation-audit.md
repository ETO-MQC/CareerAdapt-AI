# P5.2.0-B2-B1 Trusted Confirmation Audit

2026-11-02. **BLOCKED** for locked Hermes 0.19.0 at eb527605. No provably trusted Host approval issuer exists in the audited public plugin path. No Core modification or write endpoint was implemented.

## Evidence and threat model

Actual `contrib/runtime-loader.ts:17–27` explicitly describes full shared Renderer authority, without a capability sandbox. `PluginContext` exposes contributions, rest/socket, storage and i18n; SDK `host` exposes state, notifications/logs/navigation/events, gateway restart/status and generic JSON-RPC. Real Desktop enumeration records these keys; there is no proposal-bound approval API. `ctx.rest` passes body through preload/Main into authenticated HTTP. Host token proves possession of Host access, not a human decision. A plugin can call `window.hermesDesktop.api` directly; a captured real rest closure still works after Renderer plugin disable, as demonstrated by the real Host run.

Core does use native open/save dialogs (`electron/main.ts:4617,9813,9991`), but these select/export files, do not present a server-held Career diff, do not sign/bind a Proposal hash/Profile/Branch/revision/session, and do not issue a Backend-verifiable receipt. Generic gateway tools and existing tool-approval concepts cannot be renamed to a Career receipt: no audited SDK path binds those properties or independently authenticates a human decision. No claim is made that every possible Core feature was exhaustively proven incapable; the supported plugin path provides no proven mechanism satisfying this task.

| Threat | Finding |
| --- | --- |
| Agent autonomously calls Tool/API | Can submit ordinary API data; cannot be treated as consent |
| Renderer sends confirmed=true or fake modal result | Same code can construct body without a click; no attestation |
| Malicious code in same Renderer realm | Shares bridge, DOM and SDK; can forge UI/calls; neither pluginId nor plain token separates authority |

| Cross Profile or stale Revision | Read scope rejection is tested; this is not confirmation receipt target/revision validation |
| Cancel followed by late apply | Requires server cancellation/receipt invalidation ordering and atomic consume+apply; no such write path implemented |
| Trusted Backend plugin compromise | Python plugins are in-process trusted code, not an adversarial isolation boundary |

## Required design, not an implemented authority

1. AI may create an inert synthetic proposal only. Store immutable proposalId, scope (workspace/person/Profile), Branch, base Revision/id, exact typed changes, provenance and expiry on the service.
2. Canonical serialization must explicitly version field/order/encoding rules. Hash those exact target/base/change bytes server-side; UI renders the diff derived from the same stored proposal. Recompute before issuance and consumption; never hash only a user-supplied label.
3. A separately trusted Host surface must load the proposal from that service, display exact old/new values and target, and obtain an explicit accept/reject action independently of Plugin Renderer. The signing/capability credential stays outside Renderer and ordinary Agent tools.
4. Issuer would attest proposalId+hash, scope/Profile/Branch, expected Revision/id, service/session epoch, nonce, expiry, decision and audience. Backend validates issuer identity and all bindings against current server state. Rejection/cancellation must revoke outstanding challenges; late messages cannot revive them.
5. Authorized apply would check ownership, expiry, hash, revision/CAS, cancellation and nonce, then atomically consume the receipt with the canonical mutation and operation receipt. One receipt authorizes one exact proposal only; duplicate consumption rejects. Lost responses reconcile by operationId without issuing a second mutation. No formal data write exists in this PoC.

Steps 1–2 and 4–5 can be specified, but implementing a synthetic verifier with a test signing key would not prove step 3. Therefore no fake trusted issuer was built. A React button/modal, native-looking page, confirmed flag or API bearer cannot stand in for the missing authority. A separately owned confirmation application might be a new architectural candidate, but is outside this authorization; it has not been proven or selected.

## Actual negative tests and limits

Real Host requests to proposal.confirm with confirmed=true, wrong hash, foreign Profile, replay-shaped receipt, stale revision and cancelled=true all return INVALID_REQUEST because the read-only Fake Service does not expose confirmation or apply. Protocol tests assert that no result accompanies these refusals. This proves fail-closed unsupported operations only. It does **not** validate hash mismatch, cross-Profile receipt, revision, expiry, duplicate receipt or late-cancel behavior of an implemented trusted mechanism. Positive issuance, successful one-time consumption and each dedicated receipt rejection gate are **NOT RUN / BLOCKED**, not PASS. No facts, preview, PDF or formal data were written.
