# ADR A05-01：Native Career 控制面与应用侧只读桥接

日期：2026-11-06（Asia/Shanghai）。状态：**APPROVED WITH CONDITIONS / 方案 B 获得 D3 合成环境有限实施授权；实施进行中，未验收**。

## 用户审核决议（2026-11-06，当前有效）

批准 B，仅项目维护的 Hermes 0.19.0 隔离集成构建；不改外部锁定源码树、Core、Python Agent Loop，不升级 Hermes。

- C1：Main 仅 Native Lifecycle Control Plane/Synthetic Grant Controller，不是生产 Trusted Authority/身份服务。workspace→Repository 由 Application Composition Root 固定绑定。Renderer、模型、Plugin 参数均不签发身份；Session/Turn/Tool Call 首先只是关联，独立核对之前不是授权。
- C2：记录实际拓扑、进程所有权、关联、超时、断连、重启；Preload 固定严格只读控制接口，无通用 RPC/任意文件/方法/Grant Setter。优先 OS 权限保护 IPC，其他传输须额外控制。
- C3：真实 Plugin Disable 必须 Renderer→Preload→Main→Revoke；Main 提交 enabled=false、epoch递增才确认。旧 closure/在途/排队结果不得在撤权后交付。失败本地 fail closed，不显示撤权完成。Main重启/Broker断连/Renderer退出使旧grant失效，不自动恢复。Stop独立验证，不声称handler必然终止。
- C4：独立 D3 文件ledger，跨Electron/Broker重启保留 operationId、原生关联、payload hash、状态、实际执行次数、结果引用。STARTED无可靠终态=UNKNOWN；UNKNOWN只查询原operationId，禁止重执行；不构成通用exactly-once。
- C5：仅项目Main/Preload补丁、plugins-store生命周期接线、自有Python Plugin、Application Composition Root、窄Broker与测试。补丁可重复并记录SHA。禁止改run_agent.py/model_tools.py/Core/业务Gateway契约/Repository语义/Schema/FactGuard/ClaimSafety。
- C6：真实Electron、合成Profile、确定性本地传输；真实Plugin Disable触发，runner不得直接revoke。分别验收注册/执行/关联/Streaming/Stop迟到/History重启/A-B/撤权/Executed+LostACK/UNKNOWN/ledger/optIn=false。Provider资格独立报告。

未批准D4、生产issuer/真实Profile、Resume/Job/Tailoring生产工具、任何生产写入、Trusted Confirmation、迁移/新增业务数据库。保留八worktree、锁定SHA、原始失败和历史证据；不自动提交/Push/进入D4。以下“待审核”措辞是原提案历史背景，以本决议为准。

## 决策请求

建议选择方案 B：在项目维护的隔离 Host 集成中增加 Main/Preload 的窄授权控制桥，应用侧继续独占现有 Repository、QueryService、Adapter 和 Gateway。只对 D3 合成环境开放两个只读工具，不批准 D4、生产 issuer、真实资料或写入。锁定 Hermes Core/Python agent loop 不修改、不升级；外部锁定树不落盘修改。Main/Preload 的集成变化仍须用户先审核，即使采用项目内构建补丁。

这是本轮选择的实现架构需要的扩展，不是“所有合成实现都必然需要修改 Main/Core”的证明。Python plugin + 测试进程 broker 可以独立实现合成调用链；它仍需明确谁控制授权及禁用事件，不能把 runner 同时调用 revoke 当成原生 Plugin Disable 已自然实现后端撤权。本轮没有实施这一替代切片，也没有取得 D3 PASS。

## 当前证据和确切缺口

Hermes Runtime 0.19.0 / SHA `eb52760564dbba2e5971fa54bd67384e281cd3b8`；Desktop package 为 0.17.0，不混同版本。

1. Desktop `src/contrib/plugin.ts` 的 `createPluginContext` 将 `ctx.rest` 绑定插件 namespace，但闭包不检查 enabled/grant/epoch。`plugins-store.ts` 的 `setPluginEnabled(false)` 保存 Renderer 决策、执行贡献项 disposer、更新显示状态，没有后端授权撤销事务。
2. `runtime-loader.ts` 明确插件拥有 FULL app authority；它是错误隔离而非能力沙箱。不能把同一 Renderer 中的插件 ID、localStorage 或全局对象当作不可伪造的独立 issuer。
3. 本轮完整转译上述两个锁定模块并执行真实函数体，依赖使用明确列出的替身；loopback HTTP 两次均到达：第一次在 disable 前，第二次在 disable 后。贡献项释放 1 次、状态 disabled。见 `evidence/p522-a05-native-career/disable-closure-probe.json`。没有运行 Electron，没有调用 Profile Adapter，不能扩大证据等级。
4. Desktop SDK 的 `register` 是 UI contribution 注册，不是 LLM Tool 注册。原生 Python `PluginContext.register_tool` 才进入 tools registry；`model_tools.handle_function_call` 经过 tool execution middleware，传递原生 Session/Tool Call/Turn 关联。应复用此入口，不能虚构 `ctx.registerTool`。
5. A04 Adapter 在调用前、handler 前后验证授权，但只提供 issuer 接口；未接 Native Host 控制面。现有 fixture broker 不拥有正式资料与 grant，不能改名充当服务。
6. CareerAdapt 现有 Electron Browser Domain Host/READY 是另一应用组合入口；锁定 Hermes Desktop Host 没有因此自动获得它的 Renderer Repository 或 grant。下一步必须显式接入，不能将两个 Host 的已有能力混用。

结论：**既有接线不满足 C4，不是已证实一种新桥接实现不可行**。本轮选择的可靠独立控制面会触及 Main/Preload，遵守用户附件 A2 的先 ADR 后审核要求。

## 三种方案

| 方案 | 做法 | 安全与兼容性 | 结论 |
|---|---|---|---|
| A：Renderer-only 新 RPC + 测试 broker | 应用侧保存 Gateway/Repository；Python plugin 调窄 RPC；Renderer 发 enable/disable，runner 管理合成 grant | 无 Core 变更，可做合成探索；同 Renderer 的身份/禁用通知不是独立信任来源。异步 dispose、断连、崩溃与在途交付必须另定义顺序。runner 主动 revoke 仅证明 broker，不证明实际 disable 控制链 | 可选合成方案；不能借其宣称生产可信，当前未实现 |
| B：Main 授权控制 + 应用侧 Domain 桥 | 原生受控控制面持有 enabled/epoch/lease/Session 绑定；Preload 仅暴露精确命令；Python plugin 只拿 scoped invocation 能力；应用 Renderer 执行业务只读 | Main 不得拿 Repository/IndexedDB；启动/断连/禁用 fail closed。仍非任意本地恶意代码沙箱。需要最小 Main/Preload 集成审核 | **推荐，只批准 D3 合成环境实施** |
| C：扩展 Hermes Core 的通用 capability/operation 协议 | 在原生 runtime/gateway 建立统一 grants、取消和 receipt，并将应用 Domain 作为受控外部能力 | 覆盖面大、升级耦合、需锁版本和完整协议验证；可能影响其他工具与默认模式 | 本轮不推荐，超出最小接入 |

Gateway 的附件依赖 DI 可作为方案 A/B 的内部优化，但它既不产生授权来源，也不传递 disable，因此不能替代控制面。当前不改 Gateway 的依赖树。

## 方案 B 的可审查改动边界

拟变更点，而非已实现 API：

- 锁定 `apps/desktop/electron/main.ts` 的项目内集成构建：启动隔离 broker、绑定确切 WebContents/测试启动配置、控制 grant 与进程退出。不得给 Main Repository 或 Dexie。外部原始文件继续 SHA 保护。
- 锁定 `apps/desktop/electron/preload.ts` 的项目内集成构建：仅提供受控的 Career enable/disable/session-binding/invoke-result 消息；禁止通用 fs、任意 URL、任意 RPC 方法或任意 grant setter。
- Desktop `plugins-store.ts` 的 opt-in Renderer 集成：禁用通过控制桥完成“服务撤权已提交”确认后再显示 disabled；失败显示明确错误并保持本地 fail closed。不能只触发 disposer 后 fire-and-forget 网络请求。
- 新项目侧组合入口：拥有唯一应用侧 `WorkspaceRepository`，实例化现有 `ProfileQueryService`/`ProfileReadAdapter`，调用既有 Gateway/Registry 实现。不复制库、不建立第二套 Gateway 实现、不新增表。
- 新 Python plugin：使用锁定 `register_tool` 和 execution middleware，严格两个工具；只依赖标准传输和 Hermes SDK，不 import 任何 TS Domain/Repository/Dexie。原生工具名保留 `career.profile.get/search_facts`，若本地传输/provider 对 dotted name 有限制，先记录实际失败，不擅自增加同义工具。

控制消息由 Main 的固定 grant 状态和原生 runtime 上下文决定 scope；模型仅能传 sectionTypes/limit/cursor，search 另加 query。禁止模型选择 workspace/person/Profile/Session/grant/epoch/confirmed/authority。测试控制接口只属于隔离 runner，绝不能进入模型工具 schema。

## 撤权、取消、关联和断连协议

服务端 grant 绑定 workspace→现有应用 Repository、person/Profile、Session、grantId、epoch、expiry、enabled；每次入口、查询前、返回交付前均复核。禁用首先使后端 epoch 前进并 enabled=false，拒绝新请求，标记在途 operation 不可交付，随后卸载 UI。禁用确认意味着后端失效已经提交。

需定义撤权和结果交付的线性化点：在同一控制状态序列中决定结果是否可发出。撤权之后不能因旧 closure、已排队 HTTP 响应或旧 epoch 交付结果；早于撤权已交付的结果无法撤回，不谎称能够撤回。断连、Renderer 退出、Session/Profile 切换和 broker 重启都废弃旧 grant，不根据历史自动恢复授权。

关联 envelope 持有原生 sessionId/tool_call_id/turnId、桥接 requestId、测试 operationId；后两者不取代原生关联 ID。Stop 不保证强制终止已开始的底层读取，但必须停止交付、阻止 assistant 继续使用迟到结果、不重发，且不影响其他 Session。实际以 ledger 和原生事件验收。

## Executed + Lost ACK 的具体后续实验

仅合成 qualification ledger，使用隔离证据文件，不新增业务数据库或生产写协议：

1. runner 设置一次性故障；服务接受 operationId 后，将 ACCEPTED/STARTED 写入测试 ledger；实际 Adapter 调用计数加一。
2. 查询完成后记录 COMPLETED 及合成结果引用，再主动断开 ACK 通道。Host 保留 UNKNOWN，不能把服务日志直接作为 UI 已成功。
3. 保留隔离目录，关闭并重启 Electron 和 broker。通过只读 operation status 查询同一 operationId，校验原 Session/Profile/payload 关联；重启不重发 invoke，不重放历史 handler。
4. 比较进程重启前后 ledger：实际执行恒为 1；Provider/Model 恒定；工具结果关联正确，UNKNOWN 无自动重试。若只有 STARTED 没有终态，状态查询必须仍 unknown，不能补推成功。

这是定向“已完成执行、ACK 丢失”的实验，不声称任意崩溃窗口下 exactly-once，也不把 A04 requestId 当生产写幂等。

## 数据所有权和 Dexie

业务结果链保持 Python Native Tool → 窄传输 → 应用侧 Adapter → 既有 Gateway → QueryService → 同 Repository。Plugin 分发图不包含应用侧 bundle。应用侧包含 Dexie 是正确数据所有权，不能靠扫描排除隐藏；应分别扫描 Plugin 所有 runtime import/dynamic import 和应用侧完整图，标明跨进程/消息边界。测试 synthetic store 初始化与工具执行读取分开，所有业务 Store 前后快照一致。

## 验收、回滚与未来影响

实施后依附件 B/C/D 全部定向 Native Host 门禁验证，而非重新跑 A02 全矩阵。默认 optIn=false 时不安装 plugin、不创建 grant、不发请求、不改变默认 Shell；同 artifact 回归。合成配置不得包含真实 Provider 密钥或用户资料，优先本地可控 model transport；真实 Provider 若确需请求，先确认预算。

回滚关闭本轮 opt-in 开关、禁用控制桥、作废所有测试 grant，运行默认 Shell 回归。回滚不删除测试目录、历史证据或用户数据；不修改 Hermes 锁、业务 Schema、Repository 语义、Fact Guard。既有历史 manifest 和原始失败保留。Main/Preload bundle 必须重新构建和标注 SHA，不能使用旧 artifact 宣称新资格。

未来 D4 必须另行确定生产 issuer 与 workspace 绑定并独立评审。B 不批准生产 Profile 读写、可信确认或其他工具。D5/D6/D7 只复用此次控制面与成熟业务，不重造引擎；所有确认写入仍受独立可信确认/原子消费/CAS/权威 receipt 门禁约束。
