# CareerAdapt AI — P4.7b Career Agent Evaluation Baseline

Date: 2026-09-03

Baseline commit: `bf25c8a` (P4.7a)

Status: deterministic baseline established; targeted quality closure remains a later decision.

## Scope and boundary

P4.7b establishes a reproducible behavior baseline for the existing Career
Agent. It measures both user-facing outcome and Hermes tool trajectory across
representative CareerAdapt scenarios. It does not redesign the runtime or
claim that subjective writing quality is closed.

The production boundary remains:

`CareerAdapt Host → Hermes sole semantic Agent → Hermes Skills/Toolsets → CareerAdapt MCP → Domain/Workflow → WorkspaceRepository/Guards`

Agent Runtime Core, `AgentRuntimeRouter`, `HermesSupervisor`, runtime-control
auth, provider binding, MCP transport, the Agent loop, and turn lifecycle were
not changed in this phase. No second Agent, planner, evaluator service,
database, dashboard, or Dexie table was added.

The evaluation principles are representative scenarios, isolated fixtures,
reproducibility, deterministic hard graders, outcome-plus-trajectory checks,
and separate hermetic versus real-provider runs. The background references
reviewed were [Anthropic's agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents),
the [OpenHands benchmark repository](https://github.com/OpenHands/benchmarks/blob/main/README.md),
[OpenClaw runtime documentation](https://github.com/openclaw/openclaw/blob/main/docs/openclaw-agent-runtime.md),
and [OpenAI Agents running guidance](https://openai.github.io/openai-agents-python/running_agents/).

## A. Existing C1 purpose

C1 is the existing evidence-matching evaluation. Its deterministic layer
checks that candidate matches stay within the allowed fact/evidence IDs,
respect match-level and risk constraints, reject stale or unsupported
evidence, and handle prompt-injection and provider-failure cases. The optional
AI Judge is advisory; it does not replace the hard checks.

The current C1 suite contains 15 cases: 13 positive semantic cases and 2
negative cases, with 0 hard safety failures in the validation run.

Command: `pnpm test:c1:eval`

## B. Existing C2 purpose

C2 is the existing guarded adaptation/suggestion evaluation. It checks legal
and illegal rewrites, Fact Guard dispositions, evidence-reference integrity,
stale-match blocking, ownership/participation and proficiency upgrades,
numbers, prompt injection, provider failure, edit re-checks, and workflow
acceptance behavior. The current run contains 16 cases, 108 deterministic
workflow checks, and `unsafeAllowed=0`.

Command: `pnpm test:c2:eval`

P4.7b references these suites instead of copying their Fact Guard and artifact
assertions into a second evaluator.

## C. Newly covered Career Agent gap

Before P4.7b, the repository proved many domain and workflow invariants but
did not have one data-driven baseline for normal conversational behavior and
Hermes's high-level capability choice. The missing layer was the behavior
boundary between a user's natural-language request and the correct existing
CareerAdapt capability:

- direct conversation must remain tool-free;
- personal questions may use read-only Career context;
- a workflow must enter through the canonical facade;
- a successful result with an unnecessarily broad or atomic trajectory is not
  a pass;
- ambiguous assets must not be silently selected; and
- read-only turns must not mutate domain stores.

## Outcome and trajectory grading

The machine grader records these separately:

- outcome: a terminal assistant response exists and a read-only case leaves
  the observed domain stores unchanged;
- trajectory: the exact expected high-level tool sequence is used;
- safety: forbidden, atomic, diagnostic, or unallowed tools are rejected;
- economy: a per-case Career-tool budget is enforced;
- workflow: the expected canonical facade is present; and
- interaction/recovery metadata: question and recovery expectations remain in
  the case contract and are covered by mapped existing tests where the live
  harness does not duplicate them.

Hard checks are deterministic: exact tool names/order, allowed and forbidden
tools, required workflow, tool budget, terminal response presence, no-change
read-only snapshots, and the H2 unconfirmed-tool input guard. Subjective
naturalness, specificity, relevance, and clarity are deliberately not reduced
to regex assertions. Use the separate [human/content rubric](p4.7b-career-agent-human-rubric.md).

## N. Top 10 actual failure cases

There are no actual product failures in the frozen baseline: all 27 executed
cases passed and all 12 mapped cases have no failure recorded here.

During harness construction, five pre-freeze test defects were found and
corrected before freezing the artifact. They are not counted as product
failures:

1. the composer readiness helper assumed the send button was always named
   `发送消息`, although the product exposes a queued-send state;
2. the profile-intake cases incorrectly expected two Hermes facade requests,
   although the second answer is consumed at the existing Host boundary;
3. consecutive identical bridge observations were deduplicated by name rather
   than transport request ID;
4. the fake-provider route matcher let a tailoring phrase shadow Job Fit and
   export cases; and
5. a shared browser context leaked IndexedDB/session state between write-heavy
   cases.

The final harness uses terminal-message status, request-ID observation, exact
case isolation, and more specific test-only fake-provider routing. No
production behavior was changed to make these checks pass.

## O. Failure classification

The report supports `routing`, `skill`, `facade`, `domain`, `interaction`,
`artifact`, `UI`, and `runtime` classifications, with a separate `safety`
classification for hard safety violations. The frozen baseline has zero
failed cases in every classification. The five pre-freeze items above were
harness/runtime-observation defects, not classified product regressions.

## P. Fixes made in this phase

Only deterministic evaluation blockers were fixed:

- added the case schema/catalog and the plain report/grader;
- isolated each live case in a fresh browser context and Hermes restart;
- made assistant completion detection wait for a terminal `complete` or
  `failed` message;
- observed bridge requests by transport ID;
- corrected test-only fake-provider phrase routing and structured-intake
  responses; and
- made the optional real-provider command skip cleanly when credentials are
  absent.

No prompt optimization, Skill rewrite, Facade redesign, domain migration, or
runtime-loop change was introduced by P4.7b.

## Q. Deferred to P4.7c

The following remain quality-closure work rather than baseline infrastructure:

- human review of Chinese naturalness, specificity, relevance, clarity, and
  actionability;
- broader real-provider model variance and latency sampling;
- larger multi-turn, multi-asset, reload, and provider-failure scenario sets;
- content-level resume quality beyond the P4.6a structural and P4.6b tailoring
  gates; and
- targeted Skill/Facade wording changes only when a measured failure justifies
  them.

Passing infrastructure and deterministic routing does not equal Career Agent
quality closure.
